# json_requried.txt 11 条约束的调用类型分析
# 目标：区分"单次调用出 JSON → 纯 Python 消费"（适合改：关闭思考 + function_call / response_format: json_schema）
#       和"Agent 多步循环中的一环"（关思考会影响推理链路，改前必须灰度）
# 生成时间：2026-09-02
# 源文件：json_requried.txt

# ============================================================
# 分类定义（关键边界）
# ============================================================
# 【一次性调用 SINGLE_SHOT】
#   判定标准：
#     1. 一个 Prompt 模板 → 发起 1 次 LLM 请求 → 拿到 JSON → 下游 100% 是纯 Python 解析消费
#        或直接把结果传下一个完全独立的 Prompt 模板（绝不把本次 JSON 作为上下文再喂给同一个 Prompt）
#     2. 不依赖多轮 Thought→Action→Observation 的推理链
#   切换收益：
#     · 关闭 thinking → 延迟更短、token 更省、稳定性更高
#     · response_format: json_schema（或 function_call 的 parameters: schema）能从协议层保证 100% 合法 JSON，
#       无需再写 strip_markdown_code_fence、大括号贪婪匹配、parse 失败兜底那一大串防护
#   切换风险：低 ~ 中（只在"需要模型做一点点隐含推理才能出字段"时可能损失精度，
#              例如 B-3 口语"上周"映射为 start_date/end_date 需要一定常识推理能力，这部分关 thinking 可能偶尔出错）

# 【Agent 多步骤循环组成部分 AGENT_CYCLE_COMPONENT】
#   判定标准：
#     1. JSON 输出会作为"下一步 LLM 输入"的一部分（比如 ReAct Observation、Planner 执行结果）
#        再次回调同一个（或高度相似的）Prompt 模板，形成 N>1 次循环
#     2. 输出内容（Thought / first_tool_hint / replan 新任务拆分）依赖"基于上一轮结果的推理判断"，
#        不是纯抽取/纯分类
#   切换收益：关闭 thinking 理论上仍然更快、token 更省
#   切换风险：中 ~ 高
#     · ReAct 每一轮 Thought → Action 的决策质量依赖推理，关 thinking 容易产生"工具没挑对/参数没拼对/不知道要先查 A 再查 B"
#       最典型：复合问题"先查 OA 数据安全，再对比保险系统"，关 thinking 下可能第一轮就调用 Final Answer 了
#     · Replan 场景：上一轮执行给出了一堆错误或结果，需要模型基于这些结果判断"剩余计划调整哪里"，是纯粹的推理任务

【一次性调用 SINGLE_SHOT · 强烈推荐改关闭思考 + JSON schema 输出】

-- S1：A-1 · Agent 改写（Pipeline Stage1 · agent-question-rewrite.st）
   单次性质：Pipeline 改写阶段发起一次（IntentChoiceTier.FAST）→ JSON 出后直接交给
             AgentMultiQuestionRewriteService._parse_agent_rewrite() 纯 Python 处理，
             同一轮对话里不再拿这个 JSON 去喂给同一个改写 Prompt。
   推荐改法：用 response_format: json_schema（schema 字段就是现在的 6 个顶层 key），
             关闭 thinking（temperature=0.1 保持，去掉 thinking=True）。
   风险评估：★☆☆☆☆（最低）
     · 6 个字段中，complexity_analysis 是"结构化填表"，suggested_tools 是"从枚举白名单选"，
       rewrite 是"字符串抽改"，基本不需要深度推理
     · explicit_plan_hint 只是"是否出现步骤句式"的二分类 + 文本截断，不需要思考
     · 即使关 thinking 偶尔 estimated_steps 填得有点误差，ModeDecider 有 LLM 灰区精判兜底，
       后续还有 fallback_on_plan_failure 机制，不致命
   落地后可删代码：
     strip_markdown_code_fence 调用、428 行 _parse_agent_rewrite 的 json.loads
     try/except 包围可大幅简化；但上下界 clamp（step 1~10 / tool 0~10）建议保留作最后一道防线

-- S2：A-2 · 意图分类（Pipeline Stage2 · intent-classifier.st）
   单次性质：classify_targets 一次 LLM → JSON 数组 → _parse_scores 按 id 召回真实 NodeScore。
   推荐改法：response_format: json_schema，顶层声明为 {"type":"array","items":{id:string,score:number,reason:string}}，
             或 function calling 的 parameters 里声明 items.schema，关闭 thinking。
   风险评估：★☆☆☆☆（最低）
     · 是一个"给定候选列表 + 打分 + 选前 N 个"的排序任务，本质是检索/分类，不需要创造性推理
     · score 只要大致对，后续聚合还会再排一次序，精度损失容忍度高
   落地后可删代码：
     _strip_markdown_code_fence、155 行 JSONDecodeError catch、对 dict["results"] 包的兼容
     （因为 schema 强制输出数组了）

-- S3：A-3 · 模式决策（Pipeline Stage3 LLM 灰区精判 · orchestration-mode-decider.st）
   单次性质：ModeDecider._decide_by_llm_with_fallback 一次 LLM（仅灰区 ~10-20% 流量）
             → JSON → ModeDecision → Pipeline 结束，不会再喂回同一个模板。
   推荐改法：response_format: json_schema（5 字段：mode 枚举/confidence 区间/reason/initial_plan_hint/first_tool_hint），
             关闭 thinking。mode 字段建议用 enum: ["react", "plan_execute"] 在 schema 里显式声明，
             这样模型不会产出 PLAN_AND_EXECUTE 等变体，430 行的"非 plan_execute 一律 react"也能进一步简化。
   风险评估：★★☆☆☆（略高于 S1/S2，因为要对"灰区"做判断，涉及 6 条优先级规则的权衡）
     · 灰区本来就是"规则拿不准"才调 LLM，关 thinking 可能偶尔把该 plan 的判成 react，
       但下游 orchestrator 有 fallback_on_plan_failure=True，即使判 react 时执行中发现需要多步，
       也还能靠 ReAct 自己多轮循环把事情做完，所以"误判为 react"的损失远小于"误判为 plan"的损失
     · confidence < 0.55 会被代码层丢回 fallback_default_mode=react，所以即使关 thinking 出的 confidence 偏低，
       架构本身有兜底

-- S4：B-1 · RAG 查询改写（user-question-rewrite.st · 原有 RAG 管线）
   单次性质：一次 LLM → JSON → RewriteResult → 直接传下一个 RAG 检索阶段，不回环到同 Prompt。
   推荐改法：同 S1（3 字段小 schema：rewrite/should_split/sub_questions），关闭 thinking。
   风险评估：★☆☆☆☆
     · 就是纯改写/拆分判断，最简单的文本加工任务

-- S5：B-2 · 歧义澄清检查（guidance-ambiguity-check.st）
   单次性质：check_ambiguity 一次 LLM → JSON → 返回 bool + id_list + reason，后续是"是否反问用户"，
             纯判别任务，不回环。
   推荐改法：response_format: json_schema（3 字段 ambiguous/category_ids/reason），关闭 thinking。
   风险评估：★☆☆☆☆
     · 二分类"是否歧义" + 候选 ID 列表回填，不需要推理深度；Prompt 规则本身已经写得很机械
     · 解析失败本来就降级为不澄清（return False），改 function call 反而会减少"误判澄清太多"的情况

-- S6：B-3 · MCP 工具参数提取（mcp-parameter-extract.st）
   单次性质：一次 LLM → 动态参数 JSON → 直接作为工具 func(**kwargs) 的入参；后续是工具执行（代码/SDK），
             不会再喂回同一个参数抽取 Prompt。
   推荐改法：function calling 而非 response_format: json_schema。
     因为每个工具的 parameters 本身就是一个 JSON schema，可以直接作为
     function tool 的 parameters 字段传，让 LLM 走 function call 协议。好处：
       · 工具名也一起绑定在 function call 请求里，模型不会"张冠李戴"
       · 动态 schema 不用每次手拼 response_format 对象
     关闭 thinking。
   风险评估：★★★☆☆（一次性里最高的）
     · 涉及"口语→枚举映射"（"上周"→current_week、"三"→3、"要/不"→bool 等）
       需要一定的推理，关 thinking 时建议保留 temperature=0.1，必要时让 Prompt 里写几条
       映射规则（现在模板里已经有 L28-L51 专门的"数据类型处理"段落，所以就算关 thinking 影响也可控）
     · 类型不匹配时下游（工具 func 内部）会抛 TypeError/ValueError，MCP 层建议再做一次 pydantic 校验兜底
       （这个和是否关 thinking 无关，本来就该有）

-- S7：C-3 · Reflection 反思审查报告（reflection.py REFLECTION_SYSTEM_PROMPT）
   单次性质：Agent 执行完后独立阶段一次 LLM → JSON → 填 ReflectionReport dataclass；
             后续可能触发重跑整个 Agent（那时候调的是 Planner/ReAct，不是 Reflection），
             Reflection Prompt 本身不会被同一个 Prompt 回环调用。
   推荐改法：response_format: json_schema（quality_score int 0-100 + 6 个其他字段 + 强类型），
             关闭 thinking。quality_score 建议在 schema 里显式写 minimum:0, maximum:100。
   风险评估：★★☆☆☆
     · 本质是"打分 + 幻觉/完整性检查"类任务，关 thinking 会让模型"更机械地对照检查清单"，
       不会让质量分大幅漂移；反而能避免模型写一堆思考废话后忘了填 suggestions/summary 字段
     · 如果 reflection 失败本来就有降级 quality_score=50 + summary=保守评分的兜底，关 thinking
       最坏也只是触发这条降级分支，不会让 Agent 挂掉

-- S8：D-1 · ToolRouter 语义路由（tool_router_system_prompt）
   单次性质：_route_via_llm 一次 LLM → JSON 数组（工具名数组）→ 用 name 召回 BaseTool 实例；
             当前默认 force_full_pass=True，实际 0 流量，属于未来预留功能。
   推荐改法：function calling 定义一个 function "select_relevant_tools"，parameters 里
             selected_tools 是 array of enum，enum 值 = 当前 available_tools 中每个 t.name，
             这样模型不会选到不存在的工具名。关闭 thinking。
   风险评估：★☆☆☆☆
     · 本身就是工具选择，和 function calling 的"原生语义"完全契合，切换零摩擦
     · 加上 schema enum 约束后，80 行 selected_names 校验 + "没挑中就兜底前几个"的
       分支大概率可以删掉（除非模型一个都不选，但 function calling enum 基本不会空）

【Agent 多步骤循环组成部分 AGENT_CYCLE_COMPONENT · 改关闭思考要灰度/谨慎】
共 2 条（C-4 ReAct 循环 / C-2 Planner replan）

-- A-C1：C-4 · ReAct Agent 的 Action Input（react_agent.py REACT_SYSTEM_PROMPT → L35 + L85-93）
   循环性质：ReActAgent.run 循环 N 次（N=max_steps 默认 10+），每一轮的 LLM 输入
   都包含「上一轮的 Observation（工具执行结果）」，同一 Prompt 模板被回环调用 N 次。
   不推荐改关闭思考的理由：
   1. Thought 是整个 ReAct 的核心推理步骤——每一步工具的"要不要调用 / 调哪个 / 传什么参数"
      都需要模型基于 Observation 做判断；关 thinking 后模型容易直接出 Final Answer 或者
      只走第一轮就收敛，拿到的答案质量明显下降（尤其是跨数据源汇总、多步骤依赖、
      条件分支检查的复杂任务）
   2. 即使把 Action Input 包成 function calling（本身是好方案，推荐做），也建议**保留 thinking**，
      因为 function calling 只是"保证输出格式正确"，不是"替代推理过程"；
      推荐做法：function calling 替代当前手写 regex 抓 Action/Action Input 的脆弱实现
      （当前 _parse_react_step L73-94 用 regex 抓，遇到换行/json 嵌套会误判），
      但保留模型在 system prompt 里自由输出 Thought + Final Answer 的能力
   风险评估：★★★★★（最高）
     · 关 thinking 后真实线上 2 步以上任务成功率预计下降 30~50%
     · 建议：**先把"Action Input 改成 function calling（保证 JSON 合法）"单独落地，
       然后再灰度 A/B：一个实验组保持 thinking，一个实验组关 thinking，
       观察 success_rate、steps_executed、avg_turns，关 thinking 组成功率下
       降 ≥ 10% 就立即回滚**

-- A-C2：C-2 · Planner 重计划 replan（REPLAN_SYSTEM_PROMPT → L239-L273）
   循环性质：Plan-and-Execute 流程内 plan→execute 失败 → 触发 replan → 再 execute，
   形成最多 max_replan_attempts=2 次的循环（默认尝试 3 次总规划：1 次 plan + 2 次 replan）。
   不推荐改关闭思考的理由：
   1. replan 的输入是「之前 plan 的每条 task 执行结果 + 发生的错误」，需要模型判断
      "哪些子任务已经完成了 / 哪一步错了 / 新 plan 该把失败的那一步替换成什么"
      是典型的推理+诊断任务，关 thinking 容易出"把之前已完成的任务又塞回来"或
      "完全不调整原计划就原样输出"的情况
   2. replan 触发概率本来就低（execute 成功率高时几乎不触发），省不了多少 token，
      相比推理正确性的收益，这一点 token 成本不值当
   建议（折中）：不改 thinking，只把 replan 输出也套 response_format: json_schema
       （subtasks 数组 schema 和 C-1 相同），保证"格式 100% 正确"即可，
       推理过程保留自由思考。当前 _parse_subtasks 有 fallback 单任务兜底，
       加上 schema 后大概率能少触发几次 fallback，已经拿到大部分收益了

-- MID-1：C-1 · Planner 初始计划生成（PLAN_SYSTEM_PROMPT → plan()）
   性质：Plan-and-Execute 的入口，只调用一次 LLM 产出初始 SubTask[]，不会被同一个
        Prompt 回环。但是「初始计划质量」会直接影响后续 execute 的成败，进而决定
        是否需要走 replan（A-C2 循环）——所以它是"单次调用"，但"对循环质量有间接影响"。
   推荐改法（分阶段）：
     阶段 1（稳）：只加 response_format: json_schema（subtasks 数组 + 6 字段
              SubTask schema），**保留 thinking**—— 这一阶段拿到的收益是
              "格式 100% 正确，减少 fallback_1 直接回答"的概率，零风险。
     阶段 2（灰度）：关 thinking 做 A/B 实验，观察指标：
              · 计划生成后 execute 第一轮的成功率（是否需要 replan）
              · 最终 success 率（AgentOrchestrator.success=true 比例）
              · 计划粒度是否合理（会不会一个 task 里堆太多动作）
              只有三个指标没有显著下降（±3% 内）才全量
   风险评估：★★★☆☆（中等）
     · 简单计划（3~5 条 subtasks 串行）关 thinking 基本没影响
     · 复杂计划（跨工具+需要汇总+有条件分支的）关 thinking 可能产生"过度拆分"
       或"拆分不够"的问题，进而触发 replan
