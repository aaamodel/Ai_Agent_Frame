## 1. 先定标准：什么样的场景"适配你的框架"

从框架**已固化的能力**反推场景画像，而不是反过来拿场景硬套框架：

| 框架已有能力 | 对场景的隐含要求 |
|--------------|------------------|
| `file_pipe` + Milvus 混合检索（pypdf 解析、递归切分、向量+BM25+RRF） | 语料最好是**静态文档**（PDF/TXT/MD），更新频率低（月/季级） |
| `ToolRegistry` + Function Calling + 调用预算熔断 | 需要动态/结构化数据的场景要靠**加工具**解决，每加一个工具约 50~100 行 |
| `SkillManager` 渐进式披露 + `domain_profile`（Tier2 方案） | 场景人设/规则靠**一个 SKILL.md 文件**承载，零代码热插拔 |
| `RAGGenerator` 带引用生成 | 低幻觉场景（制度/法规）可强制"引用原文作答"，这是现成优势 |
| LightRAG 知识图谱 + `graph_search` 工具 | 有**实体引用关系**的语料（法条互引、人物/公司关系）可以吃到额外红利 |
| 无任务调度器 | 需要**定时自动运行**的场景（舆情监测）目前做不了，只能人工触发 |

由此得到筛选漏斗：**静态文档语料 + 问答为主 + 少量结构化查询 + 低频更新 = 最适配**。四个候选场景都是按这个漏斗筛出来的。

## 2. 场景逐个分析

### 场景 A：企业财务/报销合规助手（推荐首发）

**做什么**：员工问"去上海出差住宿标准多少""这张发票抬头对不对""报销逾期了怎么办"，agent 基于已入库的制度文档作答并标注章节；涉及职级对应标准时查结构化表格。

**资料获取**：
- ✅ **已在手**：`raw_data/企业差旅与费用报销管理办法.md`、`raw_data/发票合规与税务稽查指南.md`（两份完整制度文档，直接走 file_pipe 入库）
- 扩充渠道：
  - 财政部、国家税务总局官网公告（差旅费、增值税发票相关法规原文，免费公开，`doubao_search` 可在线补充引用）
  - 企业职级-差旅标准对照表（Excel）→ **`localexcel` 工具已内置**，无需入库，Agent 直接读表查询
  - 后续可加企业内部更多制度（考勤、采购、印章管理），同一模式复制
- 合规注意：内部制度文档入库前做脱敏（公司名/税号等，目前文档里已是占位符形式，可直接用）

**框架适配性：满分，零缺口**
- 落地只需 `垂直领域化实现方案.md` 的 **Tier1**：建 `skills/finance-compliance-assistant/SKILL.md` + 指定独立 collection（如 `finance_kb`）入库两份文档
- 工具链全现成：`rag_search`（查制度）+ `localexcel`（查标准表）+ `todo_list`（"帮我列报销材料清单"这类任务）
- `RAGGenerator` 的带引用生成恰好是这种场景的核心质量要求（"必须引用具体章节，不得估算"——SKILL.md 里写上这条规则即可生效）
- 可选后补：发票 OCR 识别工具（对接云厂商 OCR API），属于"锦上添花"，不阻塞首发

**为什么排第一**：唯一一个资料已在手、工具零缺口、且明显区别于现有投资类 skill 的场景——它同时验证了框架通用性和 Tier1/Tier2 机制，是完美的"第一个垂直场景"。

### 场景 B：投研/价值投资助手（第二步）

**做什么**：现有 5 个投资 skill（巴菲特信、能力圈、复利思维、恐惧贪婪、不发新股）之上，叠加"查某公司年报/财报数据 + 用投资框架分析"的能力。

**资料获取**：
- ✅ **已在手**：5 个投资 skill 语料（其中 `buffett-letters-skill` 含 `GITHUB_REPO.md`，语料来自 GitHub 开源仓库——这条"开源语料直接拉取"路径已被你验证过）
- 扩充渠道：
  - **巨潮资讯网（cninfo.com.cn）**：A 股上市公司年报/公告 PDF 官方免费下载，`file_pipe` 的 pypdf 已支持 PDF 解析，入库链路现成
  - **AKShare**（免费 Python 库）：行情、财报指标、宏观数据，无需 token
  - Tushare：数据更规整但需积分，可作备选
- 合规注意：**必须加免责声明规则**（SKILL.md 中写明"不构成投资建议"），这类场景的合规红线明确

**框架适配性：高，有一个小缺口**
- SKILL.md 层：已存在，`DOMAIN_PROFILE_NAME=buffett-letters-skill` 即可常驻（见垂直化方案附录）
- 缺口：**一个行情/财报查询工具**（如 `akquote_tool`：输入代码返回价格/PE/营收）。实现方式完全参照 `doubao_search.py` 的模式：写一个 builtin 模块 → 注册进 `ToolRegistry` → 加入 `allowed-tools`，约 60~100 行
- `doubao_search` 可临时兜底（让模型联网搜行情），但精度和时效不如专用工具

**为什么排第二**：语料半数在手、缺口只有一个小工具、且和你现有 skill 生态连续。但它更像"存量能力的延伸"而非"框架通用性的验证"。

### 场景 C：法律法规问答助手（观察后做）

**做什么**：基于法律法规库的问答，如"数电票开具有哪些硬性要求""劳动法对试用期工资的下限规定"。

**资料获取**：
- **国家法律法规数据库（flk.npc.gov.cn）**：官方、免费、宪法/法律/行政法规/司法解释全文可检索下载（docx/pdf）——可写一个一次性脚本批量拉取目标主题的法规入库
- 财政部/税务总局/人社部官网政策文件：免费公开
- ❌ 不建议碰：中国裁判文书网（反爬严格、限流重，获取成本高）、北大法宝/威科先行（付费版权库，入库需授权）
- 语料特点：条文式短段落 + 大量条款号 → **BM25 对"第X条"式精确匹配天然有利**，混合检索的第二条腿正好用上

**框架适配性：中高，但质量门槛高**
- 独特红利：法条之间存在引用关系（"依据《XX法》第N条"），**LightRAG 图谱 + `graph_search` 工具**可以建出"法条引用网络"，这是其他框架不容易做到的差异化
- 缺口：
  1. 条款级引用精度要求极高（错引一条比不答更糟），**必须先建评测集**（20~50 条带标准答案的问答对，人工校验），再谈上线——而框架目前没有测试套件（项目介绍文档 5.4 节已指出）
  2. 入库白名单目前仅 `.txt/.pdf`，法规库下载的 docx 需在 `kownledgebase.py` 白名单和 `file_parser` 里各加一行支持
- `RAGGenerator` 带引用生成是此场景的硬需求，同样现成

**为什么排第三**：资料获取无障碍、框架适配面大，但"低幻觉"要求倒逼你先补评测体系，工作量隐性后移。

---

### 场景 D：行业情报/竞品监测（不建议首发）

**做什么**：定时抓取行业新闻/竞品动态，生成周报摘要。

**资料获取**：公开新闻源，`doubao_search`（豆包/Tavily 双梯队）已就绪，无获取障碍。

**框架适配性：差在"没有腿"**
- 框架**没有任务调度器**，"定时自动运行"做不了，只能人工触发问答
- 产出价值依赖持续运营（每天问一遍才有情报积累），而 `MemoryManager` 长期记忆目前是按会话语义沉淀，不是情报库
- 结论：等场景 A/B 验证后、且补上调度能力（如 APScheduler 或外部 cron 调 `/chat/with_agent`）再考虑

## 3. 资料获取的四种通用模式（任何场景都逃不出这四类）

| 模式 | 做法 | 入库方式 | 已验证案例 |
|------|------|----------|-----------|
| ① 开源语料拉取 | GitHub 开源仓库 clone | 文档直接走 file_pipe | buffett-letters-skill |
| ② 官方公开库下载 | 法规库/巨潮年报，一次性脚本批量下载 | PDF/DOCX 走 file_pipe → 独立 collection | 计划中（场景 B/C） |
| ③ API 工具化 | AKShare 等，包成 ToolRegistry 工具 | **不入库**，调用时实时取 | 待做（`akquote_tool`） |
| ④ 内部文档脱敏 | 企业制度/手册 | 同①② | raw_data 两份文档 |

**核心原则一句话：静态知识走 RAG 入库，动态数据走工具实时取。** 你的框架两条路都是现成的——这四个模式里没有一个需要动核心代码。

## 5. 风险与缺口清单（诚实版）

| 缺口 | 影响 | 处置建议 |
|------|------|----------|
| 无评测集/测试套件 | 低幻觉场景（法规）质量无法验证 | 做场景 C 前先建 20~50 条 QA 评测集；顺带补 pytest |

| 上传白名单仅 .txt/.pdf | docx 语料（法规库下载）进不来 | `kownledgebase.py` + `file_parser` 各加一处，改动极小 |

| 接口无鉴权 | 任何对外场景上线前 | 网关层加 API Key（项目介绍文档 5.2 已列） |
