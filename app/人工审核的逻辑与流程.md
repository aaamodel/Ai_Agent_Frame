## 一、总开关与危险工具名单（默认全关）
闸门逻辑在 approval.py ，判定只有两条：

1. `agent_approval_enabled=False` （默认）→ 直接`return None` 放行，连`interrupt` 都不 import，线上行为与重构前完全一致；
2. 工具名不在`agent_danger_tools` （逗号分隔名单）里 → 同样放行。
只有「开关开 + 工具命中名单」才会走到`interrupt(payload)` 。配置经每请求的`GraphDeps` 注入（ deps.py 的`cfg()` ）， 
不进 state、不进 checkpoint ——这是后面"恢复时必须重建依赖"的原因。

## 二、首次运行：execute 节点内的闸门位置
危险判定刻意放在 工具真正执行之前 。两条形态都一样：

- plan 形态： execute_node.py L157-L162 ，FC 强制取参拿到 args 之后、`execute_tool_call` 之前；
- react FC 形态： execute_node.py L412-L428 ，逐条 tool_call 执行之前。
命中时调用`gate_tool_approval(deps, call, run_id=..., subtask_id=...)` ，其核心只有一行：

Python

1

`approved, comment = parse_resume_decision(interrupt(payload))`

这里发生了三件关键的事：

1. `interrupt(payload)` 抛出一个特殊的 LangGraph 中断信号 ，payload 就是 build_approval_payload 构造的 JSON 可序列化载荷
：`{type:"tool_approval", run_id, tool_name, arguments, arguments_preview, source, subtask_id, thought}` ；

2. LangGraph 捕获这个信号， 把当前图状态写入 checkpointer （state、已执行到哪个节点、pending 的 interrupt），`astream` 正常结束而不是报错；
3. execute 节点这一次的执行被"冻结"——工具没执行、预算没扣（拒绝分支也不扣）、节点没有返回任何 state 更新。
## 三、Runner 如何判定"是挂起，不是结束"
这是这套实现最严格的一条铁律，在 runner.py`_build_outcome` ：

- 不 靠 stream chunk 里的事件猜状态；
- 图驱动结束后，用 编译图的`aget_state(config)` 重新读快照（这里就是上次测试抓出来并修掉的坑：不能用 checkpointer 的`aget_tuple` ，那是`CheckpointTuple` ，没有`next/tasks/values` ）；
- is_paused_for_approval 要求 两个条件同时成立 ：`snapshot.next` 非空（有节点等着恢复） 且`snapshot.tasks[].interrupts[]` 非空。
挂起时 runner 返回`RunOutcome(paused=True, approval_payloads=[...])` ，同时也填好一个`AgentResponse` （`success=False, awaiting_approval=True` ）。chat.py 拿到后向 SSE 推一个独立事件：

JSON

1
2

`{"awaiting_approval": true, "run_id": "session:abc123...", "trace_id": "...",
 "approvals": [ {工具名/参数/子任务...} ], "done": true, "status": "awaiting_approval"}`

前端收到后渲染审批卡片，HTTP 流可以正常关闭—— 请求不挂着 ，状态躺在 Redis（内存模式则在进程内）里等。

## 四、挂起期间，什么被持久化、什么没有
进 checkpoint（state） 不进 checkpoint（RunnableConfig 注入） run_id、user_input、intent、plan、cursor、react_messages、steps、预算账本、replan 次数、
interrupt 点 model_router、memory、ToolRegistry、skill_manager、tracer、配置开关

预算计数之所以要做成"账本"序列化进 state，就是为了恢复后能还原`ToolCallBudget` （registry 本身零改动）；而每请求新建的 registry 等基础设施不序列化，恢复请求里 重建一份 即可（工具无状态）。

## 五、审批恢复：一次全新的 HTTP 请求
端点在 agent_runs.py ：`POST /api/v1/agent/runs/{run_id}/approval` ，body 只有`{approved: bool, comment: str}` 。

流程：

1. FastAPI 正常做一遍依赖注入， 重建 GraphDeps （新 registry、新 memory 连接等）；
2. 调 GraphRunner.resume() ：先读快照，不存在（TTL 过期/后端重启成内存模式）直接抛`KeyError` ，端点转成 SSE 的`run_not_found` 事件，不 500；
3. 恢复不是"从下一个节点继续"，而是：
Python

1

`async for _ in self._graph.astream(Command(resume={"approved": ..., "comment": ...}), config=config): ...`

LangGraph 的语义是—— execute 节点整个重放 ：从 checkpoint 里的节点输入重新跑一遍，再次走到`interrupt(...)` 那一行时，它不再暂停，而是 
直接返回 resume 传入的值 。所以重放是安全的：闸门之前的取参等操作重做一遍无副作用，闸门之后的工具此前根本没执行过，不存在重复调用。

4. resume 值由 parse_resume_decision 解析， fail-closed ：dict 缺字段、裸值无法识别，一律按"拒绝"处理——拿不到明确批准，危险工具就不执行。
## 六、批准 vs 拒绝，之后各走哪条路
闸门返回后节点继续，但两条分支行为不同：

- 批准 ：`gate` 返回`None` → 正常`execute_tool_call` → 观测回注 → 图继续。react 路径下一轮模型看到 tool 结果输出 Final Answer；plan 路径继续子任务提炼、cursor 推进。
- 拒绝 ：`gate` 返回 denied_observation 文本（"【人工审批拒绝】…请不要再次尝试调用该工具…"），节点 跳过执行、不耗预算 ，
把这段文本当作普通 Observation 回注模型，走正常推理收尾。注意它 不触发 replan ——拒绝是人的决定，不是工具故障。
恢复后图一路跑完，runner 再次读快照走同一套`_build_outcome` ，所以端点能处理三种结局，SSE 协议与首问完全一致：

1. 又撞上另一个危险工具 → 再推一个`awaiting_approval` （同一 run_id，可多轮审批）；
2. 失败/降级 → 流式输出友好文案 +`status:"degraded"` ；
3. 成功 → content 分片 +`status:"success"` ，载荷里都带`run_id` 。
另外`GET /agent/runs/{run_id}` 走 get_run_status ，供前端在页面刷新/重连后轮询：`paused / next / interrupts / mode_used / success` 。

`首问请求 ──prepare→plan?→execute
                          │ 命中危险工具
                          ▼
                 interrupt(payload) ──► checkpoint 落盘（Redis/InMemory）

   SSE: awaiting_approval(run_id, 工具名, 参数) ◄── HTTP 请求结束
                          │

                          │
POST /approval {approved, comment}  ◄── 全新请求，重建 deps
                          │
              Command(resume=...) ──► execute 节点重放
                          │              interrupt 直接返回决策
                 批准 ──► 执行工具        拒绝 ──► 拒绝文案当 Observation（不执行/不耗预算）
                          └──────► 图继续 → summarize → persist → END
                                          │
                   SSE: content 分片 → done(success/degraded) 或再次 awaiting_approval`

测试里两个用例 test_danger_tool_pause_and_approve / _and_deny 正好锁死了这些契约：挂起时`registry.invocations == []` ；
批准后恰好执行 1 次；拒绝后执行 0 次且仍能正常收尾。

一句话概括设计要点： 暂停判定只信快照（next + interrupts），最终状态只从快照 values 拷贝；运行时依赖随请求走、不入库；
resume 靠节点重放 + interrupt 返回值，fail-closed，拒绝零副作用。
