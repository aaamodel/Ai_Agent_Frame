# 板块三：监控（monitoring）使用文档

> 监控板块的原则只有一条：**拿不到的数据就说不可用，不用估算值填**。
> 一个「用了错误价格的完整总额」比「明说未定价」危险得多。

---

## 0. 监控要产出的东西

| 类别 | 产出 | 频率 | 用哪个文件 |
| --- | --- | --- | --- |
| 指标字典 | 四层指标定义 + 数据来源 + 告警建议 | 一次性（持续维护） | `metric_catalog.md` |
| 价格表 | 各模型 input/output 单价 | 每次调价后 | `model_pricing.yaml` |
| 日报 | 昨日请求数 / token / P95 / 成本 | 每天 | `langfuse_daily_report.py` |
| 成本换算 | 把 token 换成钱 | 按需 | `cost_calculator.py` |
| 质量追踪 | 把 eval 分数推到 Langfuse 看趋势 | 每次 CI 后 | `push_eval_scores.py` |

## 1. 文件分类

### 1.1 【指标字典】`metric_catalog.md`

四层结构（面试第 10 题的答案稿）：

| 层 | 指标 | 数据来源 |
| --- | --- | --- |
| **性能层** | QPS、P95/P99 延迟、错误率、超时率 | Langfuse observation / 压测 CSV |
| **成本层** | 单轮 token、单请求成本、按模型拆分 | Langfuse usage + 价格表 |
| **质量层** | 意图准确率、Recall@5、工具成功率、答案合格率 | `evals` 推送过来的 score |
| **稳定性层** | 熔断打开次数、降级率、模型可用率 | 熔断状态 + Langfuse 错误标记 |

每个指标都标了「**数据从哪来 / 当前是否真的采得到**」。没采到的明确写「不可用」，不写成 N/A 让人以为是 0。

### 1.2 【价格表】`model_pricing.yaml`

**当前 4 个模型的价格全部是 `null`（不是 0）**，必须你手工填：

| 模型 | tier | 说明 |
| --- | --- | --- |
| `qwen3.7-flash` | FAST | 15s 超时档 |
| `qwen3.8-max` | STANDARD | 30s 超时档 |
| `qwen3.8-max-thinking` | DEEP | 60s 超时档 |
| `text-embedding-v3` | — | 向量化 |

填写要求：
1. 从官方定价页抄，**不要凭印象**；
2. 填 `price_effective_date`（价格生效日期）——半年后回看能知道这个数字是哪个时点的；
3. 填完把顶部的 `prices_filled: false` 改成 `true`；
4. `unit: per_1k_tokens`、`currency: CNY`。

`fallback.on_unknown_model` **只支持 `warn_and_skip`**。不支持"猜价"：未知模型连 tier 都不知道，猜出来的总额看起来完整但实际上是错的。

### 1.3 【成本换算】`cost_calculator.py`

```bash
# 检查价格表填了没（exit 0，只是列状态）
python monitoring/cost_calculator.py --check-pricing

# 手工算一笔
python monitoring/cost_calculator.py --model qwen3.8-max \
        --input-tokens 12000 --output-tokens 3000

# 从压测/Langfuse 导出的 usage 文件算
python monitoring/cost_calculator.py --usage benchmark/_results/token_usage.json

# 机器可读
python monitoring/cost_calculator.py --usage xxx.json --json
```

行为约定（重要）：

| 情况 | 行为 |
| --- | --- |
| 模型已定价 | 正常算，输出明细 |
| 模型未定价 | 该项为 `None` + 警告，**不按 0 计** |
| 遇到未知模型 | 警告并跳过（不猜价） |
| 以上任一发生 | **exit 2**（CI 里能拦住"用空价格算出 0 元"的报告） |

`normalize_usage()` 兼容三种数据形状与字段别名（`usage.input` / `promptTokens` / 顶层），所以 Langfuse 导出、locust 落盘、手工 JSON 都能直接喂。

### 1.4 【日报】`langfuse_daily_report.py`

```bash
# 昨天的日报（默认）
python monitoring/langfuse_daily_report.py

# 指定日期 + 落盘
python monitoring/langfuse_daily_report.py --date 2026-09-13 --out monitoring/daily_2026-09-13.md

# 只要 JSON（给别的系统消费）
python monitoring/langfuse_daily_report.py --json

# 先看有哪些模型在用（填价格表前跑这个）
python monitoring/langfuse_daily_report.py --list-models
```

**走公开 REST API，不用 SDK**：项目用的是 Langfuse v4（OTEL），SDK 的读接口方法名在不同版本间有差异；
改用 `/api/public/traces`、`/api/public/observations`、`/api/public/scores`（Basic Auth）更稳。
同时做了字段命名兼容层：`usage.input` / `promptTokens` / 顶层三套命名都试。

凭证解析顺序：环境变量 → 应用配置。**不要把 key 写进任何产出文件。**

### 1.5 【质量追踪】`push_eval_scores.py`

```bash
# 先 dry-run 看会推什么
python monitoring/push_eval_scores.py --dry-run

# 正式推（读 evals/_results/latest.json）
python monitoring/push_eval_scores.py --run-name ci-2026-09-13

# 手工推单个指标
python monitoring/push_eval_scores.py --metric "recall@5=0.86" --metric "mrr=0.72"
```

会把 9 项评测指标推成 `eval.*` 前缀的 Langfuse score，并**自动带上阈值做对照**（score 里有 value，comment 里有阈值），这样在 Langfuse 里能直接看出离红线还有多远。

⚠️ **Langfuse 的 score 是追加写入，不去重**。同一个 trace 反复推会有多条，看趋势时按时间取最新的一条。

## 2. 三条工作流

### 2.1 每天：看成本与延迟

```bash
python monitoring/langfuse_daily_report.py --out monitoring/daily_$(date +%F).md
```

报告包含：请求数、按模型拆分的 token、P50/P95 延迟、成本（价格表填了才有）。

### 2.2 每次 CI 后：推质量分

```bash
python -m evals.report --run-all          # 产出 latest.json
python monitoring/push_eval_scores.py --run-name "ci-${GITHUB_RUN_ID}"
```

这样「质量」和「成本/延迟」出现在同一个 Langfuse 项目里，能做交叉分析——
比如"Recall@5 掉到 0.72 的那天，是不是正好切了 chunk 参数"。

### 2.3 每次调价后：更新价格表

1. 改 `model_pricing.yaml`，填价格 + `price_effective_date`
2. `prices_filled: false` → `true`
3. `python monitoring/cost_calculator.py --check-pricing` 确认 4 个模型都是 ✅

## 3. 与另两个板块的接口

```
evals/_results/latest.json  ──push_eval_scores.py──▶  Langfuse (eval.* scores)
                                                            ▲
benchmark/_results/token_usage.json ──cost_calculator.py────┤
                                                            │
Langfuse traces/observations ──langfuse_daily_report.py─────┘
```

- **评测 → 监控**：`push_eval_scores.py` 读 `evals/_results/latest.json`
- **压测 → 监控**：`cost_calculator.py --usage benchmark/_results/token_usage.json`
- **监控 → 评测**：日报里发现质量掉了，回到 `evals` 跑全量定位是哪一层掉的

### 监控层覆盖不到的（要如实说）

| 缺口 | 说明 |
| --- | --- |
| 无真实告警 | 只有指标定义与取数脚本，没有接 Prometheus / 告警通道 |
| 无 dashboard | 没有 Grafana 之类的可视化，只能看 Markdown 日报和 Langfuse |
| 无 SLO 定义 | 阈值来自压测实测基线，尚未定义正式 SLO 与错误预算 |
| 熔断状态不跨进程 | 多副本时每份独立，监控上会看到"部分实例降级" |
| 采样率未定 | Langfuse 全量 trace 在高 QPS 下成本高，需要定采样策略 |
