# 板块一：评测（evals）使用文档

> 本板块是三份文档里最详细的。原因很简单：**评测是所有后续数字的基准**。
> baseline 不准，压测的阈值校准和监控的告警线全部跟着歪。
python -m evals.runners.run_tool --limit 3                        # 默认：文件顺序（和以前一样）
python -m evals.runners.run_tool --limit 3 --order random          # 每次抽到的都不同
python -m evals.runners.run_tool --limit 3 --order random --seed 7 # 锁定同一批，可复现
python -m evals.report --run-all --limit 3 --order random          # 聚合入口同样支持

---

## 0. 先说清楚这套 eval 要回答什么

面试/复盘时真正会被追问的是这五个问题，本套 eval 一个对一个：

| 问题 | 用什么指标回答 | 数据来源 |
| --- | --- | --- |
| 意图分得准吗？ | `intent_accuracy` + `boundary_accuracy` | intent.json |
| 该召回的召回到了吗？ | `recall@5` / `hit@5` / `mrr` | rag.json |
| 召回对了，说出来的答案对吗？ | `answer_pass_rate` / `avg_fact_hit_rate` / `distractor_hit_rate` | answer.json |
| 工具选对了吗、参数传对了吗？ | `tool_success_rate` / `key_arg_recall` | tool.json |
| 一轮对话多少钱、多慢？ | `avg_tokens_per_turn` / `p95_latency_ms` | tool.json（端到端） |

还有一个「杀手锏」问题：**你怎么证明一个改动是错的？**
→ `run_chunk_regression.py`：把 chunk size 从 512 调到 1024，用同一批黄金集证明它变差了。

### 1.2 每条样本长什么样（你要的数据标注都在这）

**意图**（`intent_cases.jsonl`）

```json
{"id": "I01", "query": "员工提离职要提前多久申请？交接走哪个流程？",
 "expected_intent": "knowledge-hr", "kind": "KB",
 "boundary": false, "group": "held_out",
 "source": "人工标注（按 intent_classify_resolver 人事制度节点语义新写，避开 examples）",
 "note": "人事制度类：离职/交接属制度流程问题，答案在公司制度文档"}
```

| 字段 | 说明 |
| --- | --- |
| `query` | 问题（用户原话）。**必须**与 `intent_tree.py` 的 `examples` 无字面重合 |
| `expected_intent` | **标准答案**：必须是意图树里真实存在的叶子 id（`check_golden_purity.py` 会校验） |
| `kind` | KB / MCP / SYSTEM 通道 |
| `boundary` | **是否为易混淆边界样本**（true 的单独算一个指标） |
| `group` | `held_out` / `boundary_held_out`。标注该条**不是**从示例派生的，供审计用 |
| `source` | 标注来源（审计用）。**不允许**再写 `xxx.examples` 这类来源 |

**RAG**（`rag_cases.jsonl`）—— 四要素齐全：问题 / 标准答案 / 评分标准 / 归因信息

```json
{"id": "R01", "query": "专业版智能客服平台一年报多少钱？客户在催",
 "expected_doc_name": "公司产品知识库.md",
 "expected_doc_id": "doc-46a07d61bcdf",
 "answer_anchor": "专业版 45 万/年（≤200 席，含 +RAG 知识库、质检）——来源：第二章 2.3 版本与定价表",
 "expected_facts": ["45 万/年",
                    ["≤200 席", "200 席", "不超过 200 席"],
                    ["RAG 知识库", "知识库"],
                    "质检"],
 "judge": {"min_facts": 2, "number_strict": true,
           "order_sensitive": false, "distractors": ["15 万", "90 万"]},
 "collection": "sales_kb", "source": "人工标注（逐条核对 app/rag_data/公司产品知识库.md）"}
```

> `expected_facts` 的元素可以是**字符串**（单个要点）或**字符串数组**（该要点的多种同义写法，命中任一算命中）。
> 为什么要支持别名：中文同义表述太多（`含质检` / `与质检` / `带质检`），纯子串匹配会**系统性低估**生成质量。
> `R01` 的 `distractors = ["15 万", "90 万"]` 是标准版和旗舰版的价格——**召回对了文档、没锁定对条目**时就会命中，这类错误 Recall@5 完全看不出来。

| 字段 | 作用 | 被谁消费 |
| --- | --- | --- |
| `expected_doc_id` / `expected_doc_name` | **检索层标准答案**：算出 Recall@5 / MRR | `RunRag` → `aggregate_rag_results` |
| `answer_anchor` | **标准答案文本**（人类可读的完整答案） | 自检脚本（当"满分答案"喂给判分器验证 rubric 没写错） |
| `expected_facts` | **拆成要点的标准答案**，支持 `aliases` 别名 | `answer_quality.py` |
| `judge` | **评分标准（rubric）**：命中几个算过、要不要按序、哪些是干扰项、是否应拒答 | `answer_quality.py` |
| `unanswerable` | 知识库里**根本没有答案**，正确行为是拒答 | 跳过 Recall@5 分母；走拒答判定 |
| `distractors` | **干扰项**：邻近但不属于本题的事实 | 抓「召回对了文档、没锁定对条目」 |

**工具**（`tool_cases.jsonl`）

```json
{"id": "T16", "query": "我们的准确率承诺到底写不写在合同里？",
 "expected_tool": "rag_knowledge_search",
 "acceptable_tools": [],
 "key_args": {"query": {"value": "准确率", "aliases": ["query"]}},
 "inspect_first_n": 3,
 "source": "app/rag_data/公司产品知识库.md 2.2 关键差异化（准确率承诺写入合同 SLA）"}
```

| 字段 | 说明 |
| --- | --- |
| `expected_tool` | 期望工具名（`check_golden_purity.py` 校验它来自真实注册白名单） |
| `acceptable_tools` | 也可接受的工具（等价路径），避免"答案不唯一却判错"。**不得**引用暂不可用的飞书工具 |
| `key_args` | 关键参数；支持 `{"value":..., "aliases":[...]}` 与子串包含匹配。键名必须是该工具 schema 的真实参数（有校验） |
| `inspect_first_n` | 只看前 N 次工具调用（防止模型先试错后修正被误判） |

> ⚠️ `query` 必须落在 **`app/rag_data`（销售域）能答的内容上** ——
> 语料里没有 HR/IT/差旅/OA 文档，用那些问题测出来的是"检索不到"而不是"工具选错"。

### 1.3 为什么 `expected_doc_id` 是 `doc-xxxxxxxxxxxx` 这种形态

`RetrievalResult.id` 是**切片级 node_id**，不能直接当文档身份用。为了让 `expected_doc_id` 在**离线**状态下就能标注（不用先起 Milvus 导出真实 id），定了确定性规则：

```
doc_id = "doc-" + md5(文件名)[:12]
```

实现在 `evals/doc_ids.py`，入库脚本 `reingest_corpus.py` 用同一规则写 `metadata["document_id"]`。
好处：**chunk 512 和 1024 两个集合共享同一批 doc_id**，黄金集可以原样复用，成为干净的 A/B 对照。

### 1.4 不可答样本（R28–R32）：测幻觉的关键标注

27 条可答样本全是「一定能答上来」的题，测不出最危险的失败：**知识库没答案时，模型是老实说不知道，还是编个合理数字？**
Recall@5 完全看不到这类错误。补的 5 条分四种越界类型：

| id | 越界类型 | 考察点 |
| --- | --- | --- |
| R28 | 越界时间（问 2027 目标，语料只有 2026） | 会不会外推编造数字 |
| R29 | 越界实体属性（问竞品创始人） | 会不会从无关段落拼答案 |
| R30 | 虚构实体（不存在的客户名） | 会不会张冠李戴 |
| R31 | 越界领域（问源码仓库） | 会不会误用检索工具去猜路径 |
| R32 | 未来预测 | 会不会拿历史案例冒充预测 |

配套两条设计，缺一不可：
1. **不进 Recall@5 分母**（`aggregate_rag_results` 里 `skipped_unanswerable` 计数）——否则会无端拉低检索分数；
2. **单独判「有没有拒答」**（`judge.must_abstain`）——产出的 `abstain_correct_rate` 就是抗幻觉能力。

## 2. 指标层：完整清单

### 2.1 指标总表

| 层 | 指标键 | 中文 | 口径 | 产出文件 | 门禁键 |
| --- | --- | --- | --- | --- | --- |
| 意图 | `intent_accuracy` | 意图准确率 | 预测叶子 id == 标注 id 的比例 | intent.json | `intent.accuracy_min` |
| 意图 | `boundary_accuracy` | 边界样本准确率 | 只统计 `boundary=true` 的 5 条 | intent.json | `intent.boundary_accuracy_min` |
| 检索 | `recall@5` | Recall@5 | 期望文档在 top5 中的比例 | rag.json | `rag.recall_at_5_min` |
| 检索 | `hit@5` | Hit@5 | top5 至少命中 1 个的比例 | rag.json | `rag.hit_at_5_min` |
| 检索 | `mrr` | MRR | 首个命中名次倒数的均值 | rag.json | `rag.mrr_min` |
| 生成 | `answer_pass_rate` | 答案合格率 | 要点命中数达 `min_facts` 且无干扰项 | answer.json | `answer.pass_rate_min` |
| 生成 | `avg_fact_hit_rate` | 平均要点命中率 | 标准答案要点被说中的比例均值 | answer.json | — |
| 生成 | `distractor_hit_rate` | 干扰项命中率 | **越低越好**，命中即判不通过 | answer.json | — |
| 生成 | `abstain_correct_rate` | 应拒答正确率 | 不可答样本中确实拒答的比例 | answer.json | `answer.abstain_correct_rate_min` |
| 工具 | `tool_success_rate` | 工具调用成功率 | 期望工具出现在调用序列里（含 `acceptable_tools`） | tool.json | `tool.call_success_min` |
| 工具 | `key_arg_recall` | 关键参数命中率 | 仅统计有 `key_args` 标注的用例 | tool.json | `tool.key_arg_recall_min` |
| 成本 | `avg_tokens_per_turn` | 单轮 token | 端到端链路真实 `usage` 总量 ÷ 轮数 | tool.json | `cost.avg_tokens_per_turn_max` |
| 成本 | `p95_latency_ms` | P95 延迟 | numpy linear 口径 | tool.json | `cost.p95_latency_ms_max` |

诊断类指标（不进门禁，但排查时必看）：
`confusion`（意图混淆矩阵）、`error_rate`、`skipped_unanswerable`、`coverage`（生成层覆盖率）、
`llm_usage.calls / by_model`、每条 record 的 `top1_doc_name` / `top1_score` / `top1_content_head` / `retrieved_chunk_ids`。

### 2.2 四个必测指标的口径细节（容易讲错的地方）

- **`avg_tokens_per_turn` 取工具组**。意图组和 RAG 组也会采集 usage，但只有工具组是「改写 + 分类 + Agent 多步 + reflection」的完整一轮，才对应「一轮对话的成本」。报告里意图阶段的 usage 单独列一行做**归因**（能回答"意图阶段吃掉整轮 token 的多少"）。
- **`p95_latency_ms` 同理取端到端**。报告 `flatten_metrics` 的优先级是 `tool > rag > intent`。
- **token 是旁路采集的真实 `usage`**（monkeypatch 唯一 LLM 出口 `_chat_completion_with_langfuse`），不是字符数估算。采集不到就显示「不可用」。
- **不可答样本不计入 `recall@5`**，但计入 `abstain_correct_rate`。两条通道互不污染。
- **检索类工具的次数上限是硬编码的**：`rag_knowledge_search` 与 `knowledge_graph_search` 一律按
  「每个 rewrite 子问题 3 次」计（请求级配额 = 3 × 子问题数，未拆分即 3 次），**优先于**工具的
  `max_calls`、配置 `tool_max_attempts_<name>` 与全局默认（见
  `app/core/tools/registry.py::RETRIEVAL_TOOL_NAMES`）。目的是堵住"召回不对题后不停换同义 query
  瞎重试"——单条用例曾连调 10 次、耗时 86 秒。评测时若看到这两个工具的调用数 > 3 × 子问题数，
  说明该硬约束被改坏了。

## 3. 代码层：文件按角色分类

### 3.1 【判分内核】纯函数，无副作用，可单测

| 文件 | 职责 | 关键函数 |
| --- | --- | --- |
| `evals/metrics.py` | 检索/意图/工具/成本全部指标 + 质量门 | `recall_at_k` `hit_at_k` `mrr` `accuracy` `confusion_counts` `percentile` `token_cost` `key_arg_matches` `tool_call_success` `aggregate_*` `evaluate_gate` |
| `evals/answer_quality.py` | **生成层判分**：要点命中、顺序、干扰项、拒答检测 | `normalize_answer` `fact_hit` `fact_hit_detail` `check_order` `detect_distractors` `detect_abstain` `evaluate_answer` `aggregate_answer_results` |
| `evals/doc_ids.py` | 确定性文档 ID 规则 | `make_doc_id` `doc_id_from_path` `normalize_doc_name` |
| `evals/loaders.py` | 路径常量与 jsonl / yaml 读写 | `load_intent_cases` `load_rag_cases` `load_tool_cases` `load_thresholds` `save_results` |
| `evals/sampling.py` | **`--limit` 分层抽样 + `--order/--seed` 顺序口径（唯一真源）** | `select_cases` `select_stratified` `intent_stratum` `rag_stratum` `tool_stratum` `add_order_cli_args` `describe_selection` `run_config_of` |

设计原则：**判分逻辑全是纯函数**。这样"指标算得对不对"可以脱离 Milvus/API 单独验证——CI 的 job1 就是跑这些。

### 3.2 【执行器】真的去跑模型，需要中间件

| 文件 | 产出的指标 | 常用参数 |
| --- | --- | --- |
| `evals/runners/run_intent.py` | 意图准确率 / 边界准确率 / 延迟 / 意图阶段 usage | `--limit N`（**分层，必含边界样本**） `--order random` `--seed N` `--sleep 0.5` `--out` |
| `evals/runners/run_rag.py` | Recall@5 / Hit@5 / MRR / 延迟 | `--collection eval_kb_512` `--top-k 5` `--limit N`（**分层，必含应拒答**） `--order random` `--seed N` `--no-seed-bm25` |
| `evals/runners/run_tool.py` | 工具成功率 / 参数命中率 / 单轮 token / 端到端 P95 | `--strategy react\|plan_execute` `--limit N`（**分层，跨工具轮转**） `--order random` `--seed N` |
| `evals/runners/_runtime.py` | 装配 ModelRouter / RAGService / 意图 Pipeline（`overwrite` 恒 False） | — |
| `evals/runners/_usage.py` | 旁路采集真实 token（monkeypatch LLM 出口） | — |

工具调用的判分取自 `AgentResponse.steps` 而不是包装 `registry.invoke`。原因：steps 里还包含**被白名单拒绝**和 **HITL 挂起**的工具调用，这些正是最容易出错的地方，包装 invoke 看不到。invoke 包装降级为 `steps_incomplete` 一致性校验。

| `evals/report.py`（只读模式） | `python -m evals.report` | 不重跑，只读 `evals/_results/*.json` 重新渲染报告 |

报告的三条硬行为：
1. **单组失败不影响出报告**——Milvus 没起时该段标「未采集」并写明原因，其余照常出；
2. **0 指标时明确写「本次未采集到任何指标，质量门未生效」**——避免出现"全绿但其实是空的"误导；
3. **自动挑一个最值得讲的失败案例**，优先级：RAG 完全没召回 > 意图边界分错 > 工具选错 > 其它。

### 流程 B：首次 baseline（需要 Milvus + Redis + 模型 API）

```bash

# 4) 全量
python -m evals.report --run-all
```

⚠️ 跑之前确认 `.env` 里有可用的模型 API Key，且**不要**把 Key 写进任何报告文件。

#### `--limit` 是分层抽样，冒烟数字不能当成绩单

`--limit N` 走的是**分层抽样**（`evals/sampling.py`），**不是**「取文件前 N 条」，
三组的保证分别是：

| 组 | 保证 | 原因 |
| --- | --- | --- |
| 意图 | 必含**至少 1 条边界样本**（B01–B05） | 边界样本排在文件末尾，简单切片会一条都抽不到 |
| RAG | 必含**至少 1 条应拒答样本**（R28–R32） | 同上，应拒答排在末尾 |
| 工具 | 在**不同 `expected_tool` 之间轮转** | 黄金集按工具成簇排列，切片会扎堆在头几个工具 |

所以冒烟的作用是**验证链路通不通**，它的数字**不代表全量水平**；
成绩必须以第 4 步的全量跑为准。

#### 反复冒烟时换一批用例：`--order random` / `--seed`

分层抽样是**确定性**的，副作用是：同样的 `--limit 3` 连跑几次，测的还是那三条。
加 `--order random` 即可每次换一批：

```bash
python -m evals.report --run-all --limit 3 --order random   # 每次抽到的样本都不同
python -m evals.runners.run_tool --limit 3 --order random   # 单组也可以（三个 runner 同一套参数）
python -m evals.runners.run_tool --limit 3 --order random --seed 7   # 锁定同一批（复现失败现场）
```

⚠️ 实现口径是「**先打乱、再分层**」（`evals/sampling.py::select_cases`）：
如果只打乱最终结果，抽样集合不变、只是执行顺序变了——那并不能解决"永远测那几条"。
先打乱输入列表后，分层算法里"每层取第一条"就落在不同样本上，因此**样本本身**会变，
而保护位（边界样本 / 应拒答样本）依然每层必进 1 条。

| 参数 | 语义 |
| --- | --- |
| `--order file`（默认） | 按文件顺序，结果确定 —— **CI / 回归口径，不要改** |
| `--order random`（不传 `--seed`） | 每次运行抽到的样本与顺序都不同 |
| `--order random --seed N` | 同一 seed → 同一批用例 + 同一顺序，可复现 |
| `--order random` + 全量 | 条数不变、只是执行顺序随机（用于打散"前面的用例影响后面的记忆"这类顺序偏差） |

每次运行都会把抽样配置写进结果 JSON（`run_config`）并打印一行
`本次用例：随机顺序（seed=…），共 N 条: …`，事后能查这次到底测了哪些。

#### 样本量不足的指标：会给数，但不判分

报告里凡是标注了 `⚠️ 样本量不足` 的指标，数值照常显示给人看，
但**不进质量门**——判定的不是「分数低」，而是「这个分数还不足以被判定」。
当前下限（`evals/metrics.py`，全仓库唯一真源）：

| 指标 | 下限 | 说明 |
| --- | --- | --- |
| `p95_latency_ms` | 20 条 | n=3 时插值位置 ≈1.9，结果几乎等于最大值，测的是偶发抖动 |
| `boundary_accuracy` | 5 条 | 黄金集设计的就是 5 条边界样本，全量跑恰好达标 |

⚠️ **已知约束**：工具黄金集只有 15 条 < 20，所以**该组 P95 延迟即使全量跑也不进质量门**。
若要启用 `cost.p95_latency_ms_max` 这条红线，需要把工具集扩到 ≥20 条。

顺带两个辅助指标（本次新增，用来解释「多轮成本花在哪」）：
`median_tokens_per_turn`（中位数，抗极值）与 `llm_calls_per_request`（一轮折合几次 LLM 调用）。

**跑之前先知道要花多少 token**（离线，零成本）：

```bash
python -m evals.tools.estimate_eval_tokens          # 中位口径
python -m evals.tools.estimate_eval_tokens --compare # 跑完 baseline 后对照实测
```

默认口径下全量一轮约 **24 万 token**（输入 ~22.5 万 / 输出 ~1.9 万），
其中工具组占 ~7 成（每条要走一次意图 Pipeline + 多轮 Agent，每轮重发全文）。
本项目 FAST/STANDARD 两档都是 qwen3.7-flash，一轮全量成本在**几毛钱**量级，
调试期反复跑二十遍也可以忽略不计。真实值以 `_results/*.json` 的 `llm_usage` 为准。

### 5.2 校准方法（这是面试里最加分的一段）

拿到真实 baseline 之后：

```
合格线 = baseline 实测值 - 3~5 个百分点
```

然后**递增 `version`**。这样报告里能追溯"这次红线是哪版标准"。

两个已发生的偏离，理由要记牢：
- `p95_latency_ms_max = 45000` 而不是手册示例的 8000ms —— 本项目 DEEP tier 超时就是 60s，照抄 8000 会永远红；
- 黄金集 71 条而不是 50 条 —— 要覆盖全部 13 份可入库真实语料（`other/` 下的评测资产已排除）。

> ⚠️ **校准前置条件**：必须基于**修复 P1–P9 污染之后**的 baseline。
> 污染版（意图集抄 examples、问题集混进检索库）跑出来的数字是**虚高**的，
> 照它画线等于把标准建在错误的地基上 —— 这正是 D1 被称为"最高优先级"的原因。

### 5.3 门禁的容错设计

指标没跑出来时该项**跳过**而不是判失败。理由是「先建 eval、中间件还没好」是常见过渡态，不该把 CI 搞红。
代价是：**要通过 latest.json 里的指标数量判断这次到底测了几项**，别看到"通过"就以为全测了。
