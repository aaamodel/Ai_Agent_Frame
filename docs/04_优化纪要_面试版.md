## 〇、60 秒版本

> 我把一次真实请求拆开看，发现 token 不是花在"回答用户"，而是花在
> **规划错了 → 失败 → 重规划 → 重复喂历史**。
> 所以我没去压提示词字数，而是改了四处流程：给 Planner 真实工具白名单并在 schema 层加 enum、

> 客观指标锚在质量门的 `avg_tokens_per_turn_max = 6000`，实测基线是 **36217**。

## 一、起点：一条 trace 的钱花在哪

一次「私有化部署上线周期 + 实施费」的问答，实际发生了 **12 次 LLM 调用**（表中 12 行 generation，合计约 **2.6 万** token），而直接产出用户答案的只有最后 1 笔。

| 阶段 | ID | tokens | 问题 |
|---|---|---|---|
| 初始 Planner | `cc77af7d` | 1481 | 编造了 `sales_intelligence_query`（工具不存在） |
| task_1 参数填充 | `979f699e` | 769 | 参数 Planner 已经给过 |
| task_1 子任务总结 | `d90ec5db` | 2041 | 把整篇 SKILL.md 喂进去总结 |
| task_4 整合（失败） | `c2436f50` | 678 | 因工具被拒，输出"无法回答" |
| 证据充分性判定 | `282b063e` | 971 | `sufficient: false` |
| **Replan** | `6aa77c0b` | **7149** | **全量历史 + 整篇 SKILL.md + 错误堆栈** |
| task_2 参数填充 | `8472959a` | 1346 | 同上，白花 |
| task_2 子任务总结 | `517525b5` | 2846 | 与 task_3 检索结果高度重叠 |
| task_3 参数填充 | `64c28dab` | 1756 | 同上，白花 |
| task_3 子任务总结 | `a2705e5a` | 2810 | 与 task_2 重叠 |
| task_4 整合 | `59615499` | 1808 | 与最终汇总重复 |
| 最终汇总 + 闸门 | `fa5b0ff7` | 2422 | 保留 |

**结论**：可用 1 次检索 + 1 次生成覆盖的问题，实际烧了 12 次调用、约 2.6 万 generation token（含 embedding/包装共 3.6 万）。而检索片段 `[1]` 里"4~6 周上线"和"实施费 8 万起"本来就在同一段。

## 二、根因与改动（按收益排序）

### 1️⃣ Planner 编造工具名 → 被拒 → 触发整轮重规划（最大单笔）

**现象**：Planner 从技能名 `sales-intelligence-assistant` 派生出 `sales_intelligence_query`。

**根因（两条同时成立）**：
- `plan_generate_schema` 里 `tool_name` 只是 `str`，**没有 enum**；`strict: true` 只保证 JSON 结构合法，不保证工具真实存在；
- plan 路径的提示词里**根本没有工具清单** —— 模型唯一能看到的线索是"其余 N 个工具额度充足"（没写名字）和技能树里的 `file_read_tool`。

**改动**：
| 动作 | 位置 |
|---|---|
| 按运行时白名单**动态生成**带 enum 的 Plan schema | `llm_schemas.build_dynamic_plan_schema()` + `_inject_tool_name_enum()` |
| 提示词注入「工具名 + 能力描述 + 必填/可选参数」 | `planner._tool_catalog_block()`，plan 与 replan **都注入** |
| 白名单外工具名 → 程序化映射到 `rag_knowledge_search`，**不触发 replan** | `planner._resolve_tool_name()` + `_parse_subtasks` 业务规则⑦ |
| 兜底工具也不在白名单 → 降级为 reasoning 子任务 | 同上 |

**收益**：`c2436f50 + 282b063e + 6aa77c0b` 三笔（合计 8798）**整笔消失**。

### 2️⃣ Replan 喂全量历史（含整篇 SKILL.md）

**根因**：replan payload 是 `json.dumps(results_so_far)` 后截断 **16000** 字符，而**单条 observation 上游就被截到 8000 字符** → 整篇 SKILL.md 必然原样进 prompt。且 `results_so_far` 里成功/失败信息混在一起。

**改动**：payload 改为
```json
{ "allowed_tools": [...],
  "previous_plan":  [{id,title,action_type,tool_name}],
  "results_so_far": [{id,tool_name,status,summary≤400}],
  "error": "≤500" }
```
整体上限 **16000 → 4000** 字符，摘要优先取子任务 LLM 结论而非原始观测。

**实测**：同一场景 payload 从"单条 observation 就 8000"降到 **234 字符**。

### 3️⃣ 每个工具子任务都先花一次 LLM 填参数

**根因**：执行顺序是 `FC 取参(LLM) → tool`，而 Planner 已经在 `tool_args_hint` 里给了参数。三笔合计 **3871 tokens**。

**改动**：新增 `_fc_args.resolve_tool_args_from_hint()`，执行顺序改为
**`hint 直用（零 LLM）→ FC 取参 → 文本解析兜底`**。

安全性刻意做足（否则会回退"参数 query 不能为空"的老问题）：hint 必须可解析 + **工具全部必填参数都有非空值** + 丢弃 schema 不认识的字段；任一不满足即回退 FC。

**踩坑**：trace 里 Planner 的 hint 是**单引号** Python 字面量 `{'query': ...}`，`json.loads` 直接失败 → 解析器必须同时支持 `json.loads` 与 `ast.literal_eval`。**不修这一条，"hint 直用"永远走不通。**

### 4️⃣ 子问题被强拆成多个检索任务

**根因**：`plan_node` 的硬约束"每个子问题规划至少一个子任务"，把本可一次检索覆盖的两个子问题逼成两次工具调用 + 两次总结。

**改动**：改为「可由**同一次**工具调用（尤其同一次 rag 检索）覆盖时**必须合并**；确需不同数据源才拆」。

**预期收益**：`517525b5 + a2705e5a + 59615499`（合计 7464）→ 一次检索 + 一次生成约 2~3k，**净省约 5k**。

### 5️⃣ 提示词里的 JSON 格式废话

`response_format` 有三档降级链（`async_openai_caller._resolve_response_format`）：
`json_schema(strict) → json_object → 剥离`。
所以不能全删：**`json_object` 档 schema 不下发**，字段名只能靠提示词；且该模式要求消息体出现 "json" 字样，缺了直接 400。

**改动**：删掉"输出示例 + 逐字段类型说明 + JSON 语法错误清单"（已由 `_mini_json_repair` 的围栏/单引号/尾随逗号三层修复覆盖），保留精简字段清单与一句"只输出 JSON"。
**PLAN 900 → 417 字符，REPLAN 560 → 449 字符。**

> 顺手抓到一个真 bug：原示例写 `"action_type": "tool/reasoning"` —— **不是合法枚举值**。
> 实测 `PlanGenerateSchema.model_validate` 直接抛 `ValidationError` → 模型照抄就白烧一次 retry。

### 6️⃣ 用不上的工具与重复的搜索通道（删除项，见第四节）

## 三、工具能力改造：减少"轮次"而不是减少"字数"

一次 `file_list_tool` 的 3 连调用（一层层摸路径：`raw_data` → `raw_data/sales_intel` → 文件）说明问题不在输出长短，而在**需要几轮才能拿到事实**。

| 工具 | 改法 | 效果 |
|---|---|---|
| `file_list_tool` | 递归 `depth`（默认 3，≤8）+ 文件名 `pattern` 过滤 + 条数/字符双截断 | **3 次调用 → 1 次** |
| └ 顺带 | 噪音目录跳过（`.venv/.git/__pycache__/node_modules` + 一切点开头目录），保留显式传入时不跳过的逃生口 | 从仓库根递归不再掉进 `site-packages` |
| `local_excel_read_tool` | 换 pandas：不给 `sheet_name` 就返回**全部 sheet 的列名/行列数/前 5 行**；支持按列过滤；**分组聚合在工具内算完** | 不再猜 `Sheet1`；不让 LLM 从 50 行里心算求和；单格读取还回带列名 |
| `local_excel_write_tool` | 新增批量 `rows`（对象数组/首行即表头的二维数组）+ `write_mode`；追加走 openpyxl `ws.append()` 保格式，覆盖/新建走 `ExcelWriter` | 多行结果一次落表，不再一格一格写（每次写都触发人工审批） |
| `web_search` | Tavily 从"第二梯队（模型可选）"改成**内部降级通道**：不注册、不进白名单、不下发 schema | 模型侧只剩 1 个搜索工具名，省一份工具 schema/轮，且消除"模型自己判断该不该换工具"的不确定性 |

## 四、删除清单（负代码量）

### 4.1 `write_todos` 整体下线（评分 1/5）

它的原型是 deepagents 的 `TodoListMiddleware`，成立前提有三条，本项目**全不具备**：

| 前提 | 本项目 |
|---|---|
| 暴露 `todos` state channel | ❌ graph state 无该键，`execute()` 无状态 |
| 每轮把当前清单回注上下文 | ❌ 无回注 |
| 长 horizon 循环 | ⚠️ `max_steps=10`、总工具预算 20 |
| **致命项** | `compact_tool_observations` 只保留最近 **3** 条观测原文，更早压成 **200** 字短桩 → 写完清单再调 4 次别的工具，清单就被抹掉了 |

即：**"清单长期可见"是这个工具存在的唯一理由，而我们的历史压缩策略恰好把它抹掉。** 于是它退化成一次没有下游消费的 observation。

**删除范围**：工具本体 `todo_list.py`（整文件 **125 行**）、注册、意图树 `task` 通道（根+叶+hint）、`REGISTERED_ENABLED_TOOL_NAMES`、模式剥离机制（`PLAN_MODE_EXCLUDED_TOOLS`/`plan_mode_tool_names` 及三处调用）、改写 prompt 字面量、`SKILL.md` 施工指示、schema 快照、工具用例 T12、意图用例 I15/B04（补 B06 保持边界样本 ≥5）。

> 行数口径说明：这里是**按删除块统计**（整文件删除 + 整函数/常量删除），不是全仓 diff —— 同期还有其它工作未提交，混在一起统计没有说服力。

> 中途还做过一版"只让它在 react 可用"的方案（`prefer_mode` 翻 react + 决策层新增 `react_only_intent`），最终评估后**整条链路删除**，前一版的适配层也一并回滚 —— 这段过程本身就是很好的面试素材（先收敛再证伪）。

### 4.2 搜索通道归一

删除 `tavily_web_search` 的注册、意图白名单注入（`prepare_node` 的"梯队联动"）、`WEB_SEARCH_FALLBACK_TOOL_NAME` 常量、两个改写 prompt 的"双梯队"段落、schema 快照条目。

**顺带修掉一个沉默的降级质量漏洞**：`toolcall.py` 的 `_INVALID_OBSERVATION_MARKERS` 里只有**旧的 Tavily 失败文案**（那段文案改造后永远到不了模型），豆包自己的失败/空结果文案不在名单里 → 搜索失败会被当成**有效结果**，模型会一路换 query 空转到配额上限。已替换为当前两种真实文案。

**净效果**：注册工具 **12 → 10**；删除方式全部是"整块移除、无等价逻辑替代"（无新增类、无补偿分支）。

## 六、可验证性建设（评测侧）

优化如果不可复现，就等于没做。这轮补的：

- **`--order random --seed N`**：原先 `--limit 3` 的分层抽样是**确定性**的，连续冒烟永远测同 3 条。改为「**先打乱、再分层**」——只打乱结果集没用（样本集合不变），先打乱输入才能让每层"取第一条"落在不同样本上；保护位（边界样本、应拒答样本）依然每层必进 1 条。实测：5 次随机得到 5 种不同组合，20×5 次随机全部含边界样本。
- 抽样配置落盘进结果 JSON（`run_config`）并打印本次用例 ID，失败现场可复现。
- 黄金集纯净度校验（`check_golden_purity`）随本轮删除同步更新，`key_args` 参数名校验 0 违规。
- schema 快照 `_tool_schemas.json` 改为**从真实注册表重新生成**，不再手改 JSON。

## 八、面试追问预案

**Q：为什么说根因不是"提示词太长"？**
A：提示词优化只省几百 token；这条链路 2.6 万 token 里 8798 来自一次**本不该发生的重规划**。所以先把"计划为什么会错"解决掉，再谈压缩。

**Q：schema 加了 enum 就够了吗？**
A：不够，而且我先验证了一次——**pydantic 在父 schema 里内联子模型时不会调用子模型的 `model_json_schema` 覆写**，在子模型上注入 enum 会静默失效（代码看着加了，schema 里没有）。改成在顶层类上递归注入后才生效。即便如此，各厂商对 `anyOf` 内 enum 的执行力度不同，所以我又加了程序化映射，双保险。

**Q：怎么保证"少花 token"没有偷掉正确性？**
A：三处都设了回退：hint 直用要求必填参数齐全，否则回退 FC；replan 摘要优先用子任务结论、没有才退原始观测；白名单映射失败则降级 reasoning 而不是强行调用。**降级是"更保守"，不是"更能编"。**

**Q：删工具的依据是什么？**
A：看它依赖外围机制是否在本项目成立。`write_todos` 的价值 100% 来自"清单长期可见"，而我们的 `compact_tool_observations` 3 轮后就把观测压成短桩，且没有任何下游消费方——这不是"用得不好"，是架构前提不成立。同理 Tavily 双梯队：两个工具名 + 提示词约束让模型自己判断，不如一次代码分支确定。

**Q：改完怎么证明有效？**
A：质量门里有 `avg_tokens_per_turn_max = 6000` 的红线（实测 36217 时是 fail 的），评测侧又补了随机抽样与"本次用例 ID 落盘"，任何一次优化都能复现口径、并和 baseline 对比。

**Q：这轮改动里最容易出错的地方？**
A：模式级工具可见性必须**提示词、schema enum、执行硬闸门三处同口径**——只改提示词会留下"模型照旧习惯声明却被放行"的裂口，只改硬闸门会造成"提示词里有、执行被拒→触发 replan"。这类"同一事实存在多处副本"是最容易漂移的地方，所以我把它收敛成了单一真源函数。

## 九、补充：plan_execute 的执行过程可控化（独立变更）

> 对应 OpenSpec 变更 `plan-execute-control-protocol`。以下为**已实现**的口径。

### 起点：执行期的模型是"蒙眼"的

每个子任务执行时，模型只拿到「当前任务描述 + 历史结论文本」，**看不到计划全貌**（还剩几个 task、每个解决什么问题、用什么工具、谁成功谁失败），也**没有任何提前结束或跳过任务的能力**。因此它无从判断"答案已经够了"——即使第 2 步已取得充分证据，剩余 task 仍会逐个执行（每个 = 1 次工具调用 + 1 次提炼 LLM）。这是单轮 **21.5 次 LLM 调用 / 67,819 tokens** 的主要构成。

### 三件事

| 改造 | 要点 |
|---|---|
| 计划台账 | 每步呈现 `id / 解决的问题 / 工具 / 执行状态 / 是否解决`。**状态由 `plan` + `subtask_results` 推导**，不维护第二份状态（避免漂移） |
| 控制协议 | 结论与控制指令（`next_action` / `skip_task_ids`）在**同一次调用**产出，**不新增 LLM 调用** |
| 路由跳转 | 计算"下一个未被跳过的下标"；`finish` 归一为"跳过剩余全部"，故不新增路由分支 |

state 只新增 2 个字段（`skipped_task_ids` / `early_finish`）——它们承载的是**模型的决策**，无法从其他数据推导；其余信息一律走推导。

### 关键取舍：控制协议 vs 注册 end 工具

选控制协议的决定性理由：**它复用已经必然发生的那次提炼调用**（0 额外调用），而 `end` 工具需要模型额外发起一轮。且我们刚因"控制类工具混入业务工具清单"下线过 `write_todos`——`end` 工具会重蹈覆辙（进白名单、被 planner 规划成业务子任务、受审批与预算影响）。

### "是否解决"这一列为什么必须由模型自评

程序只能客观判定**执行失败**；而"工具成功但没答到点上"程序无从判断——**这正是前一轮"看到前 5 行就判定没数据"事故的根因**。所以分两列：执行状态（程序判）+ 是否解决（模型自评）。硬约束：执行失败的步骤由程序强制标"否"，**不采纳模型自评**（那些步骤 `skip_distill=True`，模型压根没看过数据）。

### 自愈性

提前收尾若导致证据不足，`summarize_node` 的 `sufficient` 判定会拦下并触发 replan（受 `max_replan` 限制）。所以"模型收尾过早"不会产出空答案，不需要额外硬规则。
