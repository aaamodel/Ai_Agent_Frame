# 技术提案：计划执行的可见性、收缩控制与目标锚点

> 状态：已实现（部分验证项待补齐）
> 关联规范：`openspec/changes/plan-execute-control-protocol/`、`openspec/changes/add-agent-goal/`
> 关联代码：`app/core/agent/graph/`、`app/query_intent/`

---

## 一、问题：单轮 21.5 次 LLM 调用是怎么来的

在把 plan_execute 链路迁到状态图之后，实测单轮成本被推到 **21.5 次 LLM 调用 / 67,819 tokens**——是预设红线 6,000 tokens 的 **11.3 倍**。拆开看是三个独立缺陷叠在一起：

### 1.1 执行期的模型是"蒙眼"的

每个子任务执行时，模型只拿到两样东西：**当前任务描述**，以及**历史结论文本 `ctx_str`**（只含已完成步骤的 conclusion）。

它看不到：

- 计划全貌——还剩几个子任务、每个子任务各自要解决哪个子问题；
- 各步成败状态——哪一步失败了、哪一步还在待执行。

**后果**：模型没有任何依据判断"答案已经够了"。它唯一能做的就是老实把计划跑完。

### 1.2 计划一旦生成就无法收缩

`route_after_execute` 在 plan 形态下只判断 `cursor < len(plan)`。没有提前结束、没有跳过子任务。

即使第 2 步已经取得充分证据，第 3、4 步仍会照跑——**而每一步的代价是 1 次工具调用 + 1 次结论提炼 LLM**。

### 1.3 两条路径的终止语义不对称

| 路径 | 终止方式 | 是否可提前结束 |
| --- | --- | --- |
| react | 模型不调工具、直接输出文本即写入 `final_answer`，路由转汇总 | ✅ 天然可以 |
| plan_execute | 游标走完整个计划 | ❌ 必须跑完 |

### 1.4 子问题覆盖没有保障机制

此前为了解决重复检索，引入了「多个子问题可由同一次工具调用覆盖时必须合并」的规划约束。但合并一旦未能同时覆盖全部子问题，就会有子问题**无答案**——而链路里**没有任何机制能发现这种遗漏**。

结论：**子问题的覆盖可靠性优先于合并省下的 token**。

## 二、目标与非目标

**目标**

- 让模型在每一步都能看到计划全貌与成败状态。
- 让模型能跳过冗余子任务、或在证据充分时提前收尾。
- 上述控制能力**不新增任何模型调用**。
- 每个子问题都有独立子任务覆盖，且覆盖缺失可被检出。

**非目标（范围硬约束）**

- 不提供新增子任务、修改既有子任务内容的能力——只允许「跳过」与「提前收尾」。
- 不改动 react 路径的终止语义。
- 不改动汇总阶段的证据充分性判定（复用它作为兜底）。
- 不引入新的外部依赖。

---

## 三、决策：用"控制协议"，而不是注册 `end` 工具

**决定**：在子任务结论提炼那次调用上挂结构化输出，让结论与控制指令（`next_action` / `skip_task_ids` / `reason`）一并产出。

| 对比项 | 控制协议 | 注册 `end` 工具 |
| --- | --- | --- |
| 额外模型调用 | **0**（复用已必然发生的提炼调用） | +1 轮（模型需额外发起工具调用） |
| 是否进入工具白名单 | 否 | 是 → 会被注入规划提示词，可能被规划成业务子任务 |
| 是否消耗工具预算 / 受审批影响 | 否 | 是 |
| 现有范式 | `SummaryVerdictSchema` 已验证 | 无 |

**最关键的两条**：其一，本项目**刚刚**因"控制类工具混入业务工具清单"下线过一个工具（`write_todos` 从 plan 模式剥离）；注册 `end` 工具会重蹈覆辙。其二，控制协议复用一次**本来就要发生**的调用，与压降单轮 token 的目标方向一致。

> **已否决的备选**：① 注册 `end` 工具；② 每步之后插入一个独立的"调度决策节点"——同样是额外调用。

---

## 四、决策：台账从 `plan` + `subtask_results` 推导，不维护第二份状态

每步执行前渲染一份**计划台账**给模型，每行包含：`子任务标识 / 该子任务要解决的问题 / 调用的工具（推理型子任务标明无工具）/ 执行状态`，并对已执行项追加一列「是否解决了它要解决的问题」（是 / 部分 / 否）。

关键约束：**台账由一个纯渲染函数在每次执行前生成，不写入新的状态副本。**

**理由**：维护两份状态必然漂移。本项目已有同类教训——工具白名单需要在"提示词 / schema enum / 执行硬闸门"三处同口径，任何一处漂移都会造成"提示词里有但执行被拒"的裂口。台账与计划的漂移会表现为**模型看到的进度与真实进度不一致**，比缺信息更危险。

> **已否决**：新增 `plan_ledger` 状态字段并逐步增量更新——多一份需要同步的真源。

### 「执行状态」与「是否解决」必须分列

前者是**客观的调用结果**，后者是**语义判断**，两者不等价（工具成功但没答到点上很常见）。而且「是否解决」的来源要按情况区分：

- **执行失败的子任务**（工具错误 / 空数据 / 预算熔断 / 审批拒绝）：程序**直接标为「否」**，不采纳模型自评——这些步骤根本没经过结论提炼，模型并未看到数据。
- **正常执行并完成提炼的子任务**：由模型在**同一次调用**中自评得出，不为它额外发起调用。

## 五、决策：state 只新增 2 个字段

`skipped_task_ids`（模型决定跳过的子任务）、`early_finish`（是否"答案够了"提前收尾）。

**理由**：这两个字段承载的是**模型的决策**，无法从任何其他数据推导，因此必须持久化。而"执行状态、用了什么工具、解决了哪个问题"全部可以从 `plan` + `subtask_results` 算出来，按上一节的原则不落库。

---

## 六、决策：`finish` 归一为"跳过剩余全部"

模型判定提前收尾时，把剩余未执行的子任务**全部记入 `skipped_task_ids`**，游标自然走到终点，复用既有的"计划已跑完"分支进入汇总。

**理由**：路由无需新增分支，也无需引入"提前终止"这一独立概念，状态机复杂度不增加。`early_finish` 只用于留痕，区分"是跳过了某几个"还是"整体提前收尾"。

**并且提前收尾不绕过质量闸门**：证据充分性判定仍在汇总阶段执行，判定不足时依旧会触发重规划补取证据——所以这不是绕过质量，只是不再执行冗余步骤。

---

## 七、决策：覆盖校验放在解析层，提示词只是软约束

**决定**：规划输出增加一个可选的"本子任务覆盖哪些子问题"声明字段；解析阶段校验 N 个子问题是否都被覆盖；未覆盖时触发**一次**重新规划，仍不覆盖则**记录含子问题标识的告警并继续执行**（fail-open）。

**理由**：规范要求的是 MUST 级保证，而提示词是软约束——模型完全可能继续合并。**真正的保证只能来自解析层校验。** 之所以校验后选择 fail-open 而非无限重试，是为了避免"模型坚持合并"时把链路卡死；告警留痕保证问题可观测。

> **已否决**：只回退提示词、不做校验——无法提供规范要求的保证。

---

## 八、决策：结构化输出解析失败时降级为"继续"，且不丢弃已有结论

沿用汇总节点已有的三档 `response_format` 降级链；若结构化输出不可解析但**原始文本非空**，保留该文本作为本步结论，控制指令按"继续"处理。

**理由**：控制指令是**增值能力**，不是主链路依赖。任何情况下都不能因为"调度信息没解析出来"而丢掉**已经花过钱取回**的工具数据与结论。

---

## 九、决策：重规划后清空跳过记录

`replan_node` 产出新计划时，重置 `skipped_task_ids` 与 `early_finish`（与该节点已重置 `cursor = 0` 的语义一致）。

**理由**：跳过决策是针对**旧计划**做出的。新计划是新的执行契约，不应继承旧的跳过结论——否则重规划补取证据时，恰恰需要执行的步骤可能已经被跳过。

## 十、第二个变更：`agent_goal` 目标锚点

### 10.1 为什么台账还不够

台账回答了"**每个子任务各自怎么样了**"，但没有回答"**这一切是为了达成什么**"。

模型在被要求决定"跳过某个子任务"或"提前收尾"时，只能看到一堆局部状态，无法判断某一步是否与最终目标无关，也无法判断上下文是否已经收集齐全。**缺的是一个目标锚点，不是更多状态。**

### 10.2 由改写阶段产出，不新增调用

改写阶段是**唯一**同时看到「用户原问题 + 多轮历史 + 工具/技能清单」的模型环节，目标抽象所需的全部输入都在那里；且该环节本就是组合调用，新增一个字段**不产生额外往返**。

> **已否决**：① 在意图聚合阶段单独产出——该阶段主要是向量/规则打分，加 LLM 就是新增调用；② 用规则从原问题抽取——无法产出"交付物形态"的抽象。

### 10.3 承载在 `slots["agent_goal"]`，不新增状态字段

改写结果 → Pipeline 写入 `slots["agent_goal"]` → 随 `intent.slots` 进入图状态。**既不新增意图上下文字段，也不新增图状态字段。**

**理由**：`slots` 已经是"决策层分析结果"的标准承载物（`explicit_plan_hint` / `first_tool_hint` 等先例），沿用它可以零改动地完成序列化与 checkpoint；新增平行字段会制造第二份真源——这正是上一个变更刚规避的问题。

### 10.4 台账中作为首行，而不是表格的一列

- 「跳过 / 提前收尾」的判断恰好发生在**读取台账的那一刻**，目标必须紧邻这个决策点；
- 台账本就在每一步注入，新增一行（约 20~30 字）的边际成本近乎为零；
- **但不能作为表格的一列**：目标不是"某个子任务的属性"，而是所有子任务共同的约束；作为列会让 N 行重复同一段文字，纯浪费且稀释信息。

### 10.5 三个决策点注入同一份内容

1. ReAct 模式的系统提示附加段（**Function Calling 与文本两种协议共用同一个组装函数**）；
2. 计划模式的规划提示词；
3. 子任务执行前的提示词（与计划台账一起）。

三种决策分别在这三处发生（ReAct 决定下一步调什么工具；规划决定拆几步；子任务执行决定跳过/收尾）。只注入其中一处，就等于另一种模式下仍然"不知道目标"。

### 10.6 归一化集中在解析层，读取走单一辅助函数

在改写解析处完成 `strip` → 超长截断 → 空值兜底（回退为改写后问题）；下游三处注入统一通过**一个**读取函数取目标。

**理由**：若让三个注入点各自兜底，会出现"一处回退到改写后问题、另一处注入空串"的不一致——与上一个变更里"同一事实必须单一口径"的教训同源。

**额外收益**：两条改写链路（组合调用主链路 / 组合失败后回退的两段式降级链路）的解析都收敛在**父类的同一个解析函数**上，因此归一化只写一处，两条链路行为自动一致。

### 10.7 写法与长度约束

`agent_goal` = 本次调用的**验收标准**——完成时必须交付的最终产物 / 结论形态。

提示词侧对以下五条做零容忍校验：

1. **长度**：一句话，**≤ 60 字**；超出时模型须按「交付物 + 关键约束 + 结论」的优先级自行压缩。
   ⚠️ 压缩是**提示词侧**对模型的要求；解析层只做**硬截断**兜底，**不在代码里实现"智能压缩"**。
2. **只写结果，不写过程**。
3. **禁止复述**：禁止复述原始问题或改写后问题，禁止写成步骤分解。
4. **禁止词表**（命中即不合格）：步骤词「先 / 首先 / 然后 / 接着 / 最后 / 步骤 / 计划 / 第 1 步」；空话「帮助用户 / 满足需求 / 解决问题 / 回答用户」。
5. **与 `explicit_plan_hint` 分工**：plan hint 允许列步骤，`agent_goal` 不允许——同一调用内产出，两者语义不得重叠。

**唯一例外**：当本轮产物本身就是一份步骤清单时，只写「交付操作步骤清单」，而不是把步骤逐一列出来。

**字段描述必须极简**（一行、不含示例）：该 schema 的所有描述会**逐字进入 `response_format`**，实测整份约 3.8 KB / 1.1k token，且**每次改写调用都要带上**——新增描述属于常驻成本。示例性内容放提示词文件（那里是单次注入的 system 内容）。

## 十一、可验证规格（MUST 条款摘要）

以下条款已落为规范文件，可逐条对照测试：

| 能力 | 关键 MUST |
| --- | --- |
| 计划台账 | 每次执行子任务前 MUST 呈现台账；MUST 含标识/问题/工具/状态；状态 MUST 区分「已完成 / 正在执行 / 待执行 / 已跳过 / 失败」 |
| 台账来源 | MUST 由计划与已执行记录推导；MUST NOT 维护可能漂移的独立状态副本 |
| 是否解决标注 | MUST 与执行状态**分列**；失败步骤 MUST 由程序直接标为「否」；MUST NOT 为获取该标注额外发起模型调用 |
| 跳过能力 | 模型 MUST 能指定跳过一个或多个未执行子任务；跨多个任务 MUST 直接推进到下一个未跳过项 |
| 提前收尾 | MUST 能提前结束剩余全部；MUST NOT 绕过证据充分性判定，不足时仍 MUST 可补取证据 |
| 控制指令产出 | MUST 与子任务结论在**同一次**调用中产出；解析失败 MUST 降级为「继续」且 MUST NOT 丢弃有效结论 |
| 范围约束 | MUST 仅提供跳过与提前收尾；MUST NOT 提供新增/修改子任务能力，收到此类指令 MUST 忽略并留痕 |
| 留痕 | 每次跳过或提前收尾 MUST 留下可观测记录（子任务标识 + 理由） |
| 子问题覆盖 | N>1 个子问题时 MUST 为每个子问题派发独立子任务；MUST NOT 以"可同一次调用覆盖"为由合并；未覆盖 MUST 先重规划一次，仍缺失 MUST 告警并继续 |
| 目标产出 | MUST 在改写阶段产出；MUST NOT 复述原问题；MUST NOT 为此额外发起调用 |
| 目标传递 | MUST 随状态流入图，并 MUST 可被任意节点读取；MUST NOT 维护平行副本 |
| 目标注入 | 三个决策点 MUST 注入**相同内容**；台账中 MUST 为表格上方首行，MUST NOT 作为列 |
| 目标兜底 | 缺失或为空时 MUST 回退为改写后问题并继续，MUST NOT 中断请求；超长 MUST 截断后注入 |

## 十二、风险与取舍

| 风险 | 缓解措施 |
| --- | --- |
| 模型滥用提前收尾 → 空答案 | 汇总阶段的证据充分性判定 + 重规划兜底（受重规划次数上限约束）。提前收尾**不绕过**证据闸门 |
| 模型滥用跳过 → 漏掉关键取值步骤 | 同上；且跳过后若证据不足仍会重规划。另：写操作类子任务被跳过导致动作未执行时，汇总的"操作类硬规则"会判证据不足 |
| 台账抬高每步输入体积 | 每行只放「标识 / 问题（截断）/ 工具 / 状态」四字段，不放结论全文；结论仍走既有 `ctx_str` 通道 |
| 回退合并使 token 回升 | **已知且接受**：这是用覆盖可靠性换 token。预期每次多约 1 次检索 + 1 次提炼（约 3k） |
| 结构化输出不被某些模型档支持 | 三档 `response_format` 降级链已存在，最差退化为纯文本 + 上文"降级为继续"的语义 |
| 跳过后评测口径变化（步骤数变少） | 评测指标只统计**实际执行**的步骤；需确认工具成功率与关键参数命中率的统计语义不受影响 |
| 覆盖校验 fail-open 时仍可能漏答 | 告警留痕 + 汇总阶段充分性判定兜底 |
| 目标被写成"改写后问题的副本" | 写法约束 + 提示词零容忍校验；通过 trace 抽查目标质量 |
| 三处注入内容漂移 | 单一读取函数 + 单测断言三处注入的目标文本**完全相同** |
| 每次改写调用的 `response_format` 变大 | 字段描述极简；实测增量目标 ≤ ~120 字节 |

## 十五、贯穿两个变更的设计原则

1. **同一事实只有一个口径**。状态不存可推导的信息，归一化只写一处，目标只由单一函数读取。
2. **把模型犯错当正常输入**。解析失败降级、覆盖缺失 fail-open，都以"不中断链路 + 留痕可观测"收场，而不是抛异常。
3. **增值能力不得成为主链路依赖**。控制指令、目标锚点缺失时，链路必须仍能完成请求。
4. **不为省钱牺牲正确性**。合并子问题省下的 token，比不上漏答一个子问题的代价。
5. **可靠性优先于 token**——但当控制能力可以复用已有调用时，两者不冲突。
