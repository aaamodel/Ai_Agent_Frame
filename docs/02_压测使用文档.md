# 板块二：压测（benchmark）使用文档

> **诚实红线**：本目录下的所有数字都是**本机单机环境，非生产环境数据**。
> 写入简历、报告、面试材料时必须带上这句。主动说明分得清 demo 和生产，反而加分。

---

## 0. 压测要产出的五个数字

| # | 数字 | 口径 | 从哪来 |
| --- | --- | --- | --- |
| 1 | **QPS** | 每秒完成请求数 | `locust_*_stats.csv` 的 `Requests/s` |
| 2 | **P95 延迟** | 95 分位响应时间（ms） | 同上，`95%` 列 |
| 3 | **错误率** | 失败请求 / 总请求 | 同上，`Failure Count`；明细在 `*_failures.csv` |
| 4 | **单请求平均 token 成本** | 总 token ÷ 请求数，再乘单价 | `_results/token_usage.json` + `monitoring/cost_calculator.py` |
| 5 | **熔断切换耗时** | 检测到故障 → 完成切换 | `test_circuit_breaker.py` → `熔断切换实测.md` |

前四个由 `run_bench.sh` 一次跑出，第五个单独跑。

## 1. 文件分类

### 1.1 【被测对象与问题集】

| 文件 | 说明 |
| --- | --- |
| `benchmark/queries_bench.txt` | **压测专用问题集，28 条**，纯内部依赖 |
| `benchmark/locustfile.py` | 主压测脚本（打真实后端） |
| `benchmark/locustfile_mock.py` | 三种用户：打 app 但后端接 mock / 探针 / 直接压 mock |

**为什么问题集要单独建、不复用黄金集**：黄金集里有会**真实联网**（「智齿科技最近有什么新动作」）和**真的往外部系统写数据**（「帮我在多维表格里加一条记录」）的用例。外部依赖的延迟会混进 P95，污染压测数据。
`queries_bench.txt` 里以 `#` 开头的是注释行，加载时会被跳过。

### 1.2 【Mock LLM 服务】零 API 成本测框架开销

| 文件 | 说明 |
| --- | --- |
| `benchmark/mock_llm_server.py` | 纯标准库实现的 OpenAI 兼容假服务 |

用途：**把模型延迟换成一个可控常数**，测出「框架本身的开销上限」。
真实模型的延迟是几百 ms 到几十秒，会把框架自身的开销完全淹没；mock 能回答一个真实模型下无法回答的问题——**如果模型本身不慢，你的系统能撑多少并发？**

关键参数：

```bash
python benchmark/mock_llm_server.py \
    --port 8100 --latency-ms 300 --jitter-ms 100 \
    [--fail-rate 0.05] [--hang-model qwen-max --hang-seconds 60] [--verbose]
```

端点：`POST /v1/chat/completions`、`POST /v1/embeddings`、`GET /healthz`、`GET /stats`、`GET /admin/reset`

两个刻意的设计：
- **伪向量用字符哈希做种子 + L2 归一化** → 同一文本恒得同一向量，压测结果不漂移（实测 norm²=1.0000）；
- **mock 的 token 数明确标 `mock_estimated: True`** → 不会有人把它当真实成本填进报告。

已实测通过：healthz ✅ / chat 返回标准结构 + `finish_reason: tool_calls` ✅ / embeddings 1024 维可复现 ✅ / `/stats` 计数准确 ✅ / 15 次连发 `failed=0` 且无 traceback ✅。

## 2. 环境要求（你问的设备 / API 并发）

### 2.1 硬件

| 项 | 最低 | 建议 | 备注 |
| --- | --- | --- | --- |
| CPU | 4 核 | 8 核 | Python 异步 + Milvus 都会吃核 |
| 内存 | 8 GB | 16 GB | Milvus standalone 建议 ≥ 8 GB |
| 磁盘 | SSD | SSD | Milvus 与 PG 的 IO 敏感 |

`run_bench.sh` 会自动探测 CPU 型号 / 逻辑核数 / 内存，写到 `_results/env.txt`；探测失败时用 `BENCH_CPU` / `BENCH_MEM` 环境变量手工填。

### 2.2 软件

```bash
pip install locust            # ⚠️ 当前环境尚未安装
docker compose up -d          # Milvus + Redis + PG
uvicorn app.main:app --port 8000
```

### 2.3 大模型 API 并发（**这才是真正的瓶颈**）

三个必须知道的换算：

**① 50 users ≠ 50 个在途请求**
`wait_time = between(0.5, 2.0)`，平均思考 1.25s。实际在途约 **35–44**，不是 50。

**② Agent 模式是放大器**
一次用户请求 ≈ 改写 + 意图分类 + N 步 ReAct + reflection ≈ **3~10 次 LLM 调用**。
按 `WEIGHT_CHAT=1 / WEIGHT_AGENT=2` 加权后，50 并发对后端模型 API 的压力约 **115~350 QPM**。

**③ 成本**
10 分钟 50 并发，粗估 **3200 万~9800 万 token**，账单可能几百到上千元。

### 2.4 结论：别直接冲 50 并发

建议的爬坡顺序（每一步都是为了下一步不翻车）：

```bash
# 第 1 步：mock 轮 —— 零成本，先把脚本/环境/报告流程走通
bash benchmark/run_bench.sh 50 10m --mode mock

# 第 2 步：小样本试算单次成本 —— 用 5 并发 2 分钟估算真实轮要花多少钱
bash benchmark/run_bench.sh 5 2m --mode real --no-cb

# 第 3 步：梯度爬坡 —— 10 / 25 / 50，每档 10 分钟
bash benchmark/run_bench.sh 10 10m --mode real --no-cb
bash benchmark/run_bench.sh 25 10m --mode real --no-cb
bash benchmark/run_bench.sh 50 10m --mode real --no-cb
```

**配额不够时怎么办**：诚实标注「受 API 配额限制只跑到 25 并发」，比硬凑一个失败的 50 并发数字强得多。
而且梯度爬坡能画出**并发-延迟曲线**，面试时比单点数字有话说得多。

## 3. 命令手册

### 3.1 一键跑（推荐）

```bash
bash benchmark/run_bench.sh [并发数] [时长] [--mode real|mock|both] [--no-cb]
```

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| 位置参数 1 | 50 | 并发用户数 |
| 位置参数 2 | 10m | 时长 |
| `--mode` | real | `real` 真实模型 / `mock` 假模型（零成本）/ `both` 都跑 |
| `--no-cb` | 关 | 跳过熔断专项 |

环境变量：`BENCH_HOST`（默认 `http://127.0.0.1:8000`）、`BENCH_MOCK_PORT`（8100）、`BENCH_PY`、`BENCH_LOCUST`、`BENCH_CPU`、`BENCH_MEM`。

> Windows 下用 Git Bash 执行 `.sh`。PowerShell 直接跑不了。

### 3.2 熔断专项

```bash
# 先 dry-run，确认能定位到 tier、能注入故障
python benchmark/test_circuit_breaker.py --dry-run

# 正式（挂起型故障：模拟主模型超时）
python benchmark/test_circuit_breaker.py --repeat 2 --fault hang

# 立即报错型故障
python benchmark/test_circuit_breaker.py --repeat 2 --fault instant
```

产出指标：

| 指标 | 含义 |
| --- | --- |
| `t_first_fallback_ms` | 第一次请求遇到故障时，兜底切换耗时 |
| `t_second_fallback_ms` | 第二次（已累积失败计数） |
| `t_after_open_ms` | 熔断已打开后的请求耗时 |
| `circuit_opened` | 熔断是否真的打开了 |
| `switched` | 是否切到了备选模型 |

一个容易踩的坑已在代码里规避：测试用 `PURPOSE_TIER_MAP["react"]` **动态解析 tier**，而不是写死 `fast`——否则会出现"选主候选用 STANDARD、实际调用走 FAST"，把故障注入到错误的模型上。

机制参数（已核实）：三态熔断 `AsyncModelHealthStore`，`failure_threshold=2`、`open_duration_ms=30000`。
⚠️ **该状态是进程内的，不跨进程共享**——多副本部署时每个副本各有一份熔断状态，这是已知的架构限制，报告里要如实写。

### 3.3 成本换算

```bash
# locust 跑完会落 _results/token_usage.json，交给监控板块算钱
python monitoring/cost_calculator.py --usage benchmark/_results/token_usage.json
```

未填价格时会返回 `None` + 警告 + `exit 2`，**不会静默返回 0**。

## 4. 产出物清单

一次 `run_bench.sh` 跑完，`benchmark/_results/` 下会有：

| 文件 | 内容 |
| --- | --- |
| `env.txt` | 环境说明（CPU / 内存 / 并发 / 时长 / python / locust 版本）—— 报告必须引用 |
| `locust_real_50_stats.csv` | QPS / 各分位延迟 / 失败数 |
| `locust_real_50_failures.csv` | 失败明细 |
| `locust_mock_50_*.csv` | mock 轮对照 |
| `token_usage.json` | 按模型统计的 input/output token |
| `mock_llm.log` | mock 服务日志 |
| `run_bench_<时间戳>.log` | 全程日志 |

另有 `benchmark/熔断切换实测.md`（熔断专项产出）。

### token 统计的一个口径限制

**token 成本只取自 `/api/v1/chat`**（非流式，响应里带 `usage`）。
`/api/v1/chat/with_agent` 是 **SSE 流式，响应里没有 usage**——Agent 模式的 token 只能走 Langfuse 事后统计。
这一点在 `locustfile.py` 里有明确注释，写报告时不要混用两个口径。

- mock 轮的数字（框架开销，不含模型延迟）

- 生产环境的数字（你根本没有）
