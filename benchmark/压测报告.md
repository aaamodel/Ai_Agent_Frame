### 2.2 Mock LLM 压测（`--mode mock`，零 API 成本）

这一轮**剔除模型推理时间**，用来回答「框架自身是不是瓶颈」。

| 并发 | QPS | P95 延迟 | 错误率 | 说明 |
| --- | --- | --- | --- | --- |
| 50 | 【待填】 | 【待填】 | 【待填】 | mock 延迟 300±100ms |
| 100 | 【待填】 | 【待填】 | 【待填】 | 同上 |

**取值命令**：

```bash
# 1) 起 mock
python benchmark/mock_llm_server.py --latency-ms 300 --jitter-ms 100
# 2) 应用指向 mock（必须重启应用进程）
OPENAI_API_BASE=http://127.0.0.1:8100/v1 uvicorn app.main:app --port 8000
# 3) 压测
bash benchmark/run_bench.sh 50 10m --mode mock
```

**已经实测通过的 mock 能力**（这部分不是待填，是已验证的）：

| 验证项 | 结果 |
| --- | --- |
| `/healthz` | ✅ `{"status":"ok"}` |
| `/v1/chat/completions` | ✅ 返回标准 OpenAI 结构；`finish_reason` 正确 |
| 工具调用注入（`--tool-call-ratio`） | ✅ 返回 `tool_calls`，工具名与请求里 `tools[0].function.name` 一致 |
| `/v1/embeddings` | ✅ 1024 维、**L2 归一化实测 norm²=1.0000**、同输入**可复现**（重复请求首元素相同） |
| `/stats` 计数 | ✅ `chat_requests` / `embedding_requests` / `failed_requests` 准确计数 |
| 并发健壮性 | ✅ 15 次连续请求 `failed=0`，且客户端断开不再产生 traceback |

> mock 的 `usage` 是**估算值**（`mock_estimated: true`，公式 `0.75×CJK字数 + 0.25×其他字符`）。
> 它的用途是验证 token 字段有没有被链路正确透传，**不能当作成本结论**。

## 三、熔断降级实测（简历原话：「检测到故障 → 完成切换」）

**取值命令**：

```bash
# 先看候选顺序（不花钱）
python benchmark/test_circuit_breaker.py --dry-run
# 挂起到 tier 超时（模拟主模型不响应）
python benchmark/test_circuit_breaker.py --repeat 2 --fault hang
# 立刻报错（模拟连接被拒）
python benchmark/test_circuit_breaker.py --repeat 2 --fault instant
```

| 指标 | 挂起模式(hang) | 立刻失败(instant) | 含义 |
| --- | --- | --- | --- |
| 首次降级耗时（中位） | 【待填】ms | 【待填】ms | 发起 → 拿到降级模型的成功响应 |
| 熔断后耗时（中位） | 【待填】ms | 【待填】ms | 坏模型被直接跳过，应显著更快 |
| 熔断状态打开 | 【待填】 | 【待填】 | `is_unavailable(primary) == True` |

**已核实的机制参数（来自源码，不是估算）**：

| 参数 | 值 | 出处 |
| --- | --- | --- |
| 熔断失败阈值 | `failure_threshold = 2` | `model_router_config.py:52` |
| 熔断打开时长 | `open_duration_ms = 30000`（30s） | `model_router_config.py:53` |
| FAST / STANDARD / DEEP 超时 | 15s / 30s / 60s | `PURPOSE_TIER_MAP` 注释 + tier 配置 |
| 熔断状态存放 | 进程内 `AsyncModelHealthStore`（**非跨进程共享**） | `async_model_health.py` |

> ⚠️ 最后一条很重要：熔断状态是**进程内**的。多副本部署时每个副本各自熔断，
> 会出现「副本 A 已熔断、副本 B 还在打坏模型」。这是已知局限，
> 面试被追问「多副本怎么保证熔断一致性」时要主动承认，并给出方向
> （把 health store 换成 Redis 共享状态，或把熔断上收到网关）。
>
> 写报告时必须区分两种耗时：`hang` 模式的首次降级天然接近 tier 超时值
> （要等超时才判定失败），`instant` 模式才是「检测到故障」到「切换完成」的净开销。

## 六、已知未覆盖项（诚实清单）

| 项 | 为什么没做 | 建议怎么补 |
| --- | --- | --- |
| Agent 链路的 token 成本 | SSE 响应不带 `usage`，HTTP 层拿不到 | 走 `monitoring/langfuse_daily_report.py` 读 Langfuse 的真实 usage |
| SSE 首字延迟（TTFT） | 需要与前端一致地解析 SSE 事件边界 | 用 `requests` + `iter_lines()` 自写计时，或在 `monitoring` 里按 span 统计 |
| 纯向量 vs 混合检索的 A/B | 需要再建一个纯向量集合 | 复用 `reingest_corpus.py` + 一个「禁用 BM25」的开关，即可得到"提升幅度" |
| `ToolCallBudget` 开关的 A/B | 需要两次完整压测 | 关掉预算跑一轮、打开跑一轮，才能说"失控调用降低 X%" |
| 多副本下的熔断一致性 | 单机压测不涉及多副本 | 把 `AsyncModelHealthStore` 换成 Redis 共享状态 |
| 长稳测试（>1h） | 单机跑满 1h 收益有限，且烧 token | CI 之外单独跑；重点看内存增长与连接泄漏 |
| mock 的 token 口径 | mock 无真实分词器 | 已在响应里标 `mock_estimated: true`，不参与成本结论 |
