## Why

对一条真实的 13 次大模型调用 trace 逐笔核算后，结论与"提示词太臃肿"相反：

- **可删的冗余提示词合计约 1,085 字符，只占全部输入字符（约 37,400）的 2.9%**（冷启动 hint 段 119 + 意图锚点段 66 + 技能英文说明约 800 + 目标行 100）；
- **返工链占约 20,000 字符，即 53.5%**——两次重规划及其后的每一次调用，全部花在"本可以避免的重复劳动"上。

返工的根因不是提示词长，而是**信息在链路传递中丢失或污染**：

1. 技能文档（约 4,830 字符）被整篇喂给子任务模型做自由摘要，摘要把文档里最关键的「数据资产地图」——`raw_data/sales_intel/客户线索台账.xlsx` 这类**逐字路径**——丢得一个不剩；重规划只能盲猜目录，连续两次扫 `/data` 均为空。
2. 重规划拿到的每条执行结果**归属为空**（实测每条 `id` 都是 `null`），既无法判断"哪个子任务做完了"，也没有"已试过哪些路径/查询"的结构化记录。
3. 重规划的失败原因里写着"建议检查 `/data` 目录下是否存在其他命名的销售数据文件"，而**同一份输入的 `results_so_far` 已经明确记录"在 `/data` 目录下未找到"**——模型自由生成的建议与确定性事实直接矛盾，且没有任何机制拦截。

此外，规划器被注入了两段本不该出现的输入：一段与用户问题**逐字相同**的冷启动参考段，以及一个错误的意图标签（`企业知识问答 > 实体关系图谱`，而用户问的是行业优先级策略）——后者让规划器把一个子任务分配给知识图谱检索，白跑一次工具调用与一次子任务提炼。

**参考段的来源已定位到确切根因**：改写阶段的步骤提示抽取用了子串正则 `先|步骤|第N步|数字、`，而用户问题里的「**优**先」命中了其中的「先」。命中后该函数返回的并不是匹配片段，而是**整句问题**（截到 120 字）。于是链路变成：子串巧合 → 判定为"用户明确说出了显式步骤"（附带伪造的高置信度）→ 强制走计划模式 → 整句问题被当作"步骤参考"注入规划器。**任何含「优先」或「首先」的中文请求都会走到这条路径**，这在业务问答里是极常见的措辞。

不修信息丢失而只删冗余，是在错误的维度上做优化。

**范围说明**：同一条 trace 还暴露了第 4 个问题——**纠偏粒度只有"整轮重规划"一档**（执行期完全封闭，单步问题被迫付整轮代价）。该问题已拆出到独立变更 `add-step-correction`（执行期就地纠偏：系统给出封闭候选方向集，模型只选不造），**不在本变更范围内**。

## What Changes

**一、防止信息在传递中丢失**

- 技能文档的结构化事实（数据资产路径等）必须**直接提取进运行状态**并被后续环节复用，不得仅靠模型自由摘要承担传递职责。
- 重规划的每条执行结果必须**携带子任务归属**；已试过且未取得有效数据的数据源、路径与查询必须**结构化传递**。
- 重规划的失败原因**不得包含已被记录证明为空的方向**：确定性事实优先于模型生成的建议。
- 工具失效判定改为依据**是否实际取得有效数据**，而非仅看状态字段（该 trace 中知识图谱检索失败，但状态被记为成功，从而逃过了失效去重）。

**二、大幅收窄重规划**

- 重规划 MUST 在同一轮请求内**至多发生一次**。
- 仅在**方向性错误**时允许触发：全部子任务结论均为**跑题**（有内容但无一涉及问题的核心实体、指标或时间）。缺口性质 MUST 由上游结构化给出，MUST NOT 依据自由文本推断。
- 显式排除：缺口只是"未取得有效数据"（方向正确）、或所有候选工具已被证明未取得有效数据时，MUST NOT 重规划，应转为诚实收尾。
- 重规划保留为最后手段而非主要纠偏机制；本变更**不删除该节点**（"计划方向本身错了"这类情形只有重新规划能救）。

**三、删除冗余注入**

- 与用户问题逐字相同的"冷启动参考段"整段不注入。
- 意图标签在置信度不足时不得作为硬约束注入规划器。
- 规划器侧只保留技能清单；"如何读取与遵守技能"属于执行侧说明。

## Capabilities

### New Capabilities

- `agent/mode-decision`: "用户是否明确给出步骤"这一判定的依据与产物内容——该判定直接决定本轮走哪种编排模式，并决定步骤参考段的内容。
- `agent/planner-input`: 规划器提示词中由前置阶段注入的参考块，其必要性判定与内容重复判定——哪些块可以进入、哪些必须整段不进入。
- `agent/skill-document-loading`: 技能文档被读取后，其中的结构化事实如何提取、存放并传递给后续环节，以及摘要在其中被允许承担的角色边界。
- `agent/replan-context`: 重规划的**触发边界**（何时允许、何时禁止、次数上限）与**输入完整性**（结果归属、已试路径与数据源、失败原因累积、输入内部不得自相矛盾）。

### Modified Capabilities

（无。既有 6 个能力——`agent/agent-goal`、`agent/excel-query`、`agent/plan-execute-control`、`agent/plan-subtask-allocation`、`evals/rag-quality-gate`、`platform/llm-call-budget`——的需求行为均不变。）

## Impact

**受影响代码**

- `app/core/agent/graph/nodes/plan_node.py`：规划器输入块的组装（参考段必要性、意图锚点置信度判定、技能清单压缩）。
- `app/core/agent/planner.py`：重规划的输入组装与结果压缩（`_compact_results_for_replan` 的归属字段）。
- `app/core/agent/graph/nodes/replan_node.py`：失败工具去重口径与触发前置校验。
- `app/core/agent/graph/builder.py`：重规划的触发条件收窄与次数上限（`route_after_execute` / `route_after_summarize`）。
- `app/core/agent/graph/nodes/execute_node.py`：子任务提炼前的技能文档处理与结论产出。
- `app/core/agent/graph/nodes/summarize_node.py`：缺口性质需结构化给出（供重规划触发判定使用），而非仅自由文本。
- `app/core/agent/graph/state.py`：结构化事实（数据资产路径等）的存放键。

**不新增**：工具；工具实现与参数；执行期的控制指令通道（该通道的扩展属于 `add-step-correction`）。

**不受影响**

- 工具实现、工具参数与工具白名单算法。
- 执行器的控制协议（跳过 / 提前收尾 / 就地纠偏）语义——本变更不改它，只在其之外收窄重规划。
- `agent/excel-query` 的表格能力披露；`platform/llm-call-budget` 的超时与重试预算；`agent/agent-goal` 的目标注入；`agent/plan-subtask-allocation` 的子问题覆盖校验。

**风险**

- 技能文档的结构化提取依赖文档结构（表格）。文档格式不规范时提取会失败，此时必须回退到既有行为而非中断链路。
- 提高注入门槛（参考段必要性、意图置信度）会使某些请求少一条提示信息；需保证缺失时链路仍完整（与 `agent/agent-goal` 的"缺失不得阻断链路"取向一致）。
- **收窄重规划后，部分原本会被重规划救回的情形将改为诚实收尾**。这是有意的取舍：宁可给出诚实的部分答案，也不要在同一方向上重复试探。步级问题的兜底由 `add-step-correction` 承担。
- 重规划从 2 次降到 1 次可能降低"救回率"；若观测到明显下降，应优先加强执行期纠偏（`add-step-correction`），而不是放宽本变更的触发条件。
