## Context

动机见 `proposal.md - Why`。此处只补充设计所必需的现状约束：

1. **plan 路径当前没有"提前出口"**。`route_after_execute` 在 plan 形态下只看 `cursor < len(plan)`，必须把计划跑完；而 react 路径天然可以结束——模型不调工具、直接输出文本即写入 `final_answer`，路由随即转汇总。两条路径的终止语义不对称。
2. **执行期的模型输入里没有计划**。`ctx_str` 仅由已执行步骤的 `subtask_id / title / conclusion` 拼成，既无状态也无未执行步骤，模型无法判断"还剩多少、是否够了"。
3. **子任务提炼是一次必然发生的模型调用**（每个非失败步骤一次），且当前是自由文本输出、无结构化约束。
4. **`summarize_node` 已有成熟范式**：用 `SummaryVerdictSchema` 在一次调用内同时产出 `answer` 与 `sufficient` 判定，并已接入三档 `response_format` 降级链。
5. **本轮之前刚因"控制类工具混入业务工具清单"下线过一个工具**（`write_todos` 从 plan 模式剥离）。这是一条重要的反面经验。

## Goals / Non-Goals

**Goals**

- 让模型在每一步都能看到计划全貌与成败状态。
- 让模型能跳过冗余子任务、或在证据充分时提前收尾。
- 上述控制能力**不新增任何模型调用**。
- 每个子问题都有独立子任务覆盖，且覆盖缺失可被检出。

**Non-Goals**

- 不提供新增子任务、修改既有子任务内容的能力（范围硬约束）。
- 不改动 react 路径的终止语义。
- 不改动 `summarize_node` 的判定逻辑（复用其充分性判定作为兜底）。
- 不引入新的外部依赖。

## Decisions

### D1：用"控制协议（结构化输出）"，而不是注册 `end` 工具

**决定**：在子任务提炼那次调用上挂结构化输出，让结论与控制指令（`next_action`、`skip_task_ids`、`reason`）一并产出。

**理由**

| | 控制协议 | 注册 `end` 工具 |
|---|---|---|
| 额外模型调用 | **0**（复用已必然发生的提炼调用） | +1 轮（模型需额外发起工具调用） |
| 是否进入工具白名单 | 否 | 是 → 被注入规划提示词，可能被规划成业务子任务 |
| 是否消耗工具预算 / 受审批影响 | 否 | 是 |
| 现有范式 | `SummaryVerdictSchema` 已验证 | 无 |

最关键的理由是第一条与最后一条：本项目刚因"控制类工具混入业务工具清单"下线过 `write_todos`，`end` 工具会重蹈覆辙；而控制协议复用现有调用，与压降单轮 token 的目标一致。

**备选（已否决）**：① 注册 `end` 工具；② 在每步之后插入一个独立的"调度决策节点"——同样是额外调用，否决。

### D2：台账从 `plan` + `subtask_results` 推导，不维护第二份状态

**决定**：台账用一个纯渲染函数在每次执行前生成，输入是计划本身与已执行记录，不写入新的状态副本。

**理由**：维护两份状态必然漂移。本项目已有惨痛教训——工具白名单需要"提示词 / schema enum / 执行硬闸门"三处同口径，任何一处漂移都会造成"提示词里有但执行被拒"的裂口。台账与计划的漂移会表现为"模型看到的进度"与"真实进度"不一致，比缺信息更危险。

**备选（已否决）**：新增一个 `plan_ledger` 状态字段并在每步增量更新——多一份需同步的真源。

### D3：state 只新增 2 个字段

`skipped_task_ids`（被模型决定跳过的 id）、`early_finish`（是否"答案够了"提前收尾）。

**理由**：这两个字段承载的是**模型的决策**，无法从任何其他数据推导，因此必须持久化。而"状态、工具、解决的问题"全部可从 `plan` + `subtask_results` 算出，按 D2 不落库。

### D4：`finish` 归一为"跳过剩余全部"

**决定**：模型判定提前收尾时，把剩余未执行的子任务全部记入 `skipped_task_ids`，游标自然走完，复用既有 `cursor >= len(plan)` 分支进入汇总。

**理由**：路由无需新增分支，也无需引入"提前终止"这一独立概念，减少状态机复杂度。`early_finish` 仅用于留痕区分"是跳过了某几个"还是"整体提前收尾"。

### D5：子问题覆盖校验放在解析层，提示词只是软约束

**决定**：规划输出增加可选的"该子任务覆盖哪些子问题"声明；解析阶段校验 N 个子问题是否都被覆盖；未覆盖时重新规划一次，仍不覆盖则记录告警并继续（fail-open）。

**理由**：spec 要求的是 MUST 级保证，而提示词是软约束——模型完全可能继续合并。真正的保证只能来自解析层校验。之所以校验后选择 fail-open 而非无限重试，是为了避免"模型坚持合并"时把链路卡死；告警留痕保证问题可观测。

**备选（已否决）**：只回退提示词、不校验——无法提供 spec 要求的保证。

### D6：结构化输出解析失败时降级为"继续"，且不得丢弃已有结论

**决定**：沿用 `SummaryVerdictSchema` 的三档降级链；若结构化输出不可解析但原始文本非空，保留该文本作为本步结论，控制指令按"继续"处理。

**理由**：控制指令是**增值能力**，不是主链路依赖。任何情况下都不能因为"调度信息没解析出来"而丢掉已经花钱取回的工具数据与结论。

### D7：重规划后清空跳过记录

**决定**：`replan_node` 产出新计划时，重置 `skipped_task_ids` 与 `early_finish`（与它已重置 `cursor = 0` 语义一致）。

**理由**：跳过决策是针对**旧计划**做出的；新计划是新的执行契约，不应继承旧的跳过结论。否则 replan 补取证据时，恰恰需要执行的步骤可能已被跳过。

## Risks / Trade-offs

| 风险 | 缓解措施 |
|---|---|
| 模型滥用提前收尾 → 空答案 | 已有 `summarize_node` 的 `sufficient` 判定 + `replan` 兜底（受 `max_replan` 限制）。提前收尾**不绕过**证据闸门 |
| 模型滥用跳过 → 漏掉关键取值步骤 | 同上；且跳过后若证据不足仍会 replan。另：写操作类子任务被跳过导致动作未执行时，汇总的"操作类硬规则"会判 `sufficient=false` |
| 台账抬高每步输入体积 | 每行只放"标识 / 问题（截断）/ 工具 / 状态"四个字段，不放结论全文；结论仍走既有 `ctx_str` 通道 |
| 回退合并使 token 回升 | 已知且接受：这是用覆盖可靠性换 token。预期每次多约 1 次检索 + 1 次提炼（约 3k） |
| 结构化输出不被某些模型档支持 | 三档 `response_format` 降级链已存在，最差退化为纯文本 + D6 的降级语义 |
| 跳过后评测口径变化（`steps` 变少） | 评测指标只统计**实际执行**的步骤；需在实现时确认 `tool_success_rate` / `key_arg_recall` 不受影响 |
| 覆盖校验 fail-open 时仍可能漏答 | 告警留痕 + 汇总阶段充分性判定兜底 |

## Migration Plan

1. 无数据迁移、无外部依赖变更。
2. 建议在编排配置中增加一个开关（默认开启）以包裹"跳过 / 提前收尾"的生效逻辑；回滚方式为关闭该开关，链路退回"跑完整个计划"的既有行为。
3. 上线后需在 Langfuse 上确认三项：跳过/提前收尾的触发率、单轮 token 是否下降、提前收尾后因证据不足而 replan 的比例（该比例过高说明模型收尾过早，需收紧提示词）。

## Open Questions

- 台账中"该子任务解决哪个问题"是否需要显式关联到子问题序号（而非沿用现有描述文本）。这会影响规划输出的字段设计，但不影响本设计的其余部分与任务拆分；可在实现首个任务时定稿。
