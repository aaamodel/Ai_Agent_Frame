## Context

动机见 `proposal.md - Why`。此处只补充设计所必需的现状约束。

1. **超时链路现状**：执行器里 `asyncio.wait_for(...)` 包在**候选级**调用外层，而候选级调用内部还会触发底层客户端的自动重试——两者共用一个 `tier.timeout_ms`。客户端由 `async_build_openai_client(candidate, provider)` 构建，**从不接收 timeout**，于是落到底层 SDK 默认（读超时 600s、自动重试 2 次）。实测日志形态：`Retrying request ... in 0.47s` 紧接 `tier-timeout (50000ms(tier=fast))`。
2. **LightRAG 侧现状**：`light_rag.py` 通过 `openai_complete_if_cache(...)` 直连，**硬编码** `api_key` / `base_url`，只从 tier 候选池借用模型名；思考开关写死为 `enable_thinking=False`。它还有自己的一套并发/超时体系（`priority_limit_async_func_call(max_size=4, llm_timeout=...)`，由全局配置派生 worker / health 超时，实测日志 `timeout=240`），以及自带的 `llm_response_cache`（图谱抽取的重复调用靠它省成本）。
3. **表格工具现状**：`_render_overview` 已给出全部列名 + 前 N 行 + 下钻提示，但**不区分列的用途**；聚合侧通过 `pd.to_numeric(errors="coerce")` 判定某列可否参与数值聚合。**披露口径必须与聚合口径同源**，否则会出现"概览说可聚合、实际聚合报错"。
4. **评测侧现状**：`metrics.sample_gate()` + `metrics["sample_insufficient"]` + `report.flatten_metrics()` 已是**现成机制**——被标记的指标数值照常展示，但不进入质量门。现有下限：`MIN_SAMPLES_PERCENTILE=20`、`MIN_SAMPLES_BOUNDARY=5`。检索指标（`recall@k` / `hit@k` / `mrr`）共用同一个判分分母（`scored`），但**都没有接入该机制**。
5. **配置现状**：`.env` 中 `LLM_TIER_FAST=glm-4.7`（单候选）、`LLM_TIER_FAST_TIMEOUT_MS=50000`。`dependencies.py` 里"（15s 超时）"的注释已过期，属于本次要一并纠正的口径漂移。

## Goals / Non-Goals

**Goals:**

- 让"一次调用最多等多久"可由配置直接推导，且**每一次尝试独立计时**。
- 让重试次数显式、可观测：日志能区分"某次尝试超时"与"重试后仍失败"。
- 让知识图谱抽取链路的模型调用与所属档位使用**同一套**超时/重试/思考开关参数。
- 让表格概览自证"这张表能怎么聚合"，消除为聚合而做的探测性读取。
- 让检索类指标接入既有样本门，小样本不再产生假红。

**Non-Goals:**

- 不新增或更换模型、不调整 tier 候选池。
- 不把 LightRAG 接入统一路由（仅做参数同源；理由见 D4）。
- 不改检索算法与分块参数。
- 不修「优先」被误判为步骤提示的缺陷（另开变更）。

## Decisions

### D1：`tier.timeout_ms` 的语义改为「单次尝试预算」

**决定**：配置中的 tier 超时解释为**一次尝试**的上限，而不是"整个候选（含重试）"的上限。

**理由**：现状正是后一种语义，导致"两次尝试共用一个预算"——第二次尝试注定被掐掉，看起来像"模型算得慢"。按单次解释后，超时值可直接回答"一次调用最多等多久"。

**代价**：最坏总耗时由 `T` 变为 `(1 + 重试次数) × T`，因此必须同时限制重试次数（D2）。

**备选（已否决）**：① 只把 `timeout_ms` 调大——治标，且会同步抬高 P95；② 保留共享预算但只为超时场景加日志——问题本身仍在。

### D2：重试改由我们这一层控制，关闭底层客户端的隐式重试

**决定**：客户端以 `max_retries=0` 构建；重试由执行器显式实现：`for attempt in 1..(1 + 重试次数)`，每次尝试各施放一个独立的超时预算。

**理由**：隐式重试有两宗罪——① 与候选级超时共用预算（D1）；② **吞掉真实错误**，日志里只剩一行 `Retrying request`，无法判断首次失败的原因。显式重试让"第几次尝试、耗时多少、失败类型"全部可记录，也让重试次数可按档位配置（交互档位少重试或不重试）。

**默认取值**：重试次数默认 **1**（即最多 2 次尝试）。交互档位承受不起 `3 × T` 的最坏耗时，而"完全不重试"会把瞬时故障直接暴露为失败，在单候选档位上等于放弃可用性。

**备选（已否决）**：保留 SDK 重试并把外层预算设为 `(1+retries) × T`——不解决"第二次尝试没有独立预算"的观测问题，也无法按尝试记录耗时。

### D3：HTTP 层设超时，外层 `wait_for` 退化为安全网

**决定**：客户端显式设置 `timeout = 单次预算`；外层的 `asyncio.wait_for` 使用**略大于**单次预算的宽限值，仅用于兜住"连 HTTP 层超时都没能触发"的挂死情况。

**理由**：若两层取同一数值，外层 `wait_for` 会先触发并抛出无法区分来源的 `TimeoutError`。让 HTTP 层先超时，可以拿到带 provider 语境的失败信息（"是提供方慢"而非"是我们掐的"），外层只做最后一道保险。

**实现约束（读码得出，影响任务拆分）**：客户端是按**模型**缓存的（`_resolve_client` 以 `model_id` 查表），而**同一个模型可能同时出现在多个档位且各档预算不同**——例如 `glm-4.7` 同时在 FAST 与 STANDARD。因此单次超时**不能固化在客户端构建上**，必须在**每次请求**时传入（底层 SDK 支持请求级 `timeout`）。`max_retries=0` 属客户端级属性，可在构建时设定。

**备选（已否决）**：① 只保留外层 `wait_for`、不给客户端设超时——就是现状，此时底层 SDK 会按自己的默认（600s）等待，语义完全脱节；② 按「模型 × 档位」重建客户端以固化超时——同一模型多档位时会产生冗余客户端，且失去按 `model_id` 查表的简洁性。

### D4：LightRAG 采用「参数同源」，不接入统一路由

**决定**：从同一份档位配置中读取（模型名、单次超时、重试次数、思考开关）供知识图谱抽取链路使用；**不**把它的调用改为经统一路由。

**理由**：接入路由虽然治理最彻底（超时/熔断/追踪统一），但有两处硬冲突：

- **熔断计数会被污染**：图谱抽取以 `max_size=4` 的并发批量调用，量级远高于对话链路，会把路由的健康计数打满，进而**误伤对话链路的候选选择**；
- **会丢掉它自带的 LLM 响应缓存**：抽取阶段对同一分块会重复请求，缓存是实打实的成本节省。

因此本次取"参数同源"：让行为与档位一致，同时不动它的并发与缓存机制。

**已知局限（接受）**：不接入路由意味着它仍不进统一熔断与调用级追踪。若后续要彻底统一，应先把"抽取类调用"与"交互类调用"的健康计数**分桶**，再接路由。

**备选（已否决）**：注入自定义 `llm_model_func` 走路由——见上述两处冲突。

### D5：可聚合能力的判定口径必须与聚合口径同源

**决定**：概览中"可聚合数值列"的判定，复用聚合时使用的同一套数值转换与判定逻辑；"可用作分组列"取非数值且取值基数在合理区间的列。

**理由**：Excel 列常被读成文本（带单位、带括号的列名尤其常见），若概览按 dtype 判断、聚合按"可转换性"判断，就会出现**披露说能聚合、调用却报"没有可聚合的数值"**——比不披露更糟，因为它会把模型引向一次注定失败的调用。两者同源后，披露等价于"这个调用一定成立"。

**体积控制**：每张表最多给出一组可直接照抄的聚合参数示例；分组列/数值列本身只列名，不展开组合。

**备选（已否决）**：用启发式词表（如列名含"区域/产品线"就判为分组列）——会与真实数据漂移，且失败方式不可预期。

### D6：只给「首个命中排名的均值」加样本门，同分母指标保持不变

**决定**：新增一个检索类最小样本量常量，**只应用于 `mrr`**；复用既有的 `sample_gate` 与 `sample_insufficient` 机制，不改报告渲染逻辑。`recall@k` / `hit@k` 保持既有行为（不设门）。

**理由**：本次目的是消除"单条用例的排名 → 整体被判红"这个假阳性，而该假阳性正是由 `mrr` 触发的。`recall@k` / `hit@k` 在小样本下取值稳定（只有 0/分数，不像排名倒数那样对位置敏感），暂不动它们可以把改动面收到最小。

**下限取值**：与既有分位数下限取同一数值（20）。当前黄金集 32 条、其中 5 条为应拒答样本不计入分母，**全量跑 27 条 ≥ 20 达标**，因此全量结论不受影响；小样本冒烟则不再判定。

**已知不协调（接受）**：`mrr` 与 `recall@k` / `hit@k` 共用同一判分分母，因此小样本下会出现"`mrr` 不判定、`recall@5` 仍参与判定"的状态。已评估为**可接受**——两者的样本敏感性不同（排名倒数对位置极敏感，命中比例不敏感），且该状态只出现在样本不足的冒烟场景。若将来需要统一，只需把同一个下限常量同样应用于另外两个键。

**备选（已否决）**：三者统一加门——语义更自洽，但改动面更大，且本轮无证据表明 `recall@k` / `hit@k` 存在同类假阳性。

## Risks / Trade-offs

| 风险 | 缓解措施 |
|---|---|
| 单次预算独立后最坏总耗时上升 | 重试次数默认 1（D2）；日志记录尝试序号与耗时，便于发现"总在重试"的档位 |
| 关闭隐式重试后，瞬时故障直接暴露为该候选失败 | 保留一次显式重试；单候选档位失败时向上抛出可读错误（而非静默降级） |
| LightRAG 仍不进统一熔断与调用级追踪 | 本次接受并记录（D4）；后续若接入，需先把抽取类与交互类的健康计数分桶 |
| 概览体积上升 | 每表最多一组示例（D5）；实测每表新增约 2~3 行，且能省掉一次工具往返（其响应远大于此） |
| 披露口径与聚合口径漂移 | 强制复用同一判定逻辑（D5），并在测试中断言"披露出的参数真的能跑通" |
| 检索指标加门后，将来黄金集缩小会导致召回也不判定 | 下限与既有分位数常量同源，随黄金集规模一起调整；报告中会明确标注"样本量不足"及所需条数 |
| 超时语义变更会影响所有链路（横切） | 语义变更集中在执行器与客户端构建两处；用"单次尝试独立计时"的行为测试覆盖，而非只测配置读取 |

## Migration Plan

1. **无数据迁移、无外部依赖变更。**
2. **配置语义变更需知会**：`LLM_TIER_*_TIMEOUT_MS` 由"整个候选预算"变为"单次尝试预算"。现有 `50000` 在单次语义下属于宽松取值，可直接沿用；若要维持原有总时长观感，应下调该值。
3. 上线顺序：先落 D2/D3（客户端与执行器），再落 D4（LightRAG 参数同源），最后落 D5/D6（工具与评测，互不影响）。
4. 回滚：D1~D3 可通过恢复客户端的隐式重试与共享预算回滚；D5/D6 可单独移除披露与样本门。
5. 上线后需确认：① 超时日志能区分"单次尝试超时"与"重试后失败"；② 表格概览披露的参数可直接跑通聚合；③ 小样本冒烟不再因检索指标判红，全量结论不变。

## Open Questions

- LightRAG 是否最终接入统一路由（P-D4 的备选）。取决于未来是否需要把抽取类调用纳入统一熔断与追踪；不影响本次的 specs 与任务拆分。
