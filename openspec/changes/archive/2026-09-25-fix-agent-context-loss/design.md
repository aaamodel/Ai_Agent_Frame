# Design：上下文丢失与提示词污染

动机与范围见 `proposal.md`（Why / What Changes）。本文件只记录设计层面必需的现状与决策。

**范围边界**：同一条 trace 还暴露了"纠偏粒度只有整轮重规划一档"的问题，已拆出到独立变更 `add-step-correction`。本变更只负责：信息传递的修复、重规划的收窄、冗余注入的删除。

## Context

实现本变更所需的现状（均已核实）：

- **规划器提示词有两处拼装点**。`plan_node._build_planner_skills_block()` 先拼〔本轮目标 → 意图锚点 → 冷启动 hint → 子问题约束 → 技能段〕，随后 `PlannerAgent.plan()` 在其后追加工具清单、预算段与「当前用户新目标」。这意味着：**任何以 `## ` 开头的注入块都会插在技能段标题与技能内容之间**。
- **步骤提示的唯一来源是改写阶段的规则抽取**。`_extract_plan_hint_if_present()` 用子串正则 `先|步骤|第\s*\d+\s*步|\d+[\.\)、]\s*` 判定，命中后返回 `原问题[:120]`。该值经 `explicit_plan_hint` → `ModeDecision.initial_plan_hint`（仅 `decision_source="explicit_hint"` 分支赋值）→ `slots["initial_plan_hint"]` → 规划器提示词。即：**一个函数同时决定了"走哪种模式"和"注入什么参考段"**。
- **子任务的结论由该次调用内的模型自评产出**，工具原始观测（`obs_str[:6000]`）与台账、历史结论同批进入提示词。技能文档正是在这里被整篇读入又被摘要掉。
- **执行期只能收缩，且重规划是唯一的纠偏通道**。`SubTaskOutcomeSchema` 已有 `next_action`(continue/finish) 与 `skip_task_ids`，但与结论同一次调用的通道里**没有"换源"这一档**；`route_after_execute` 的文档字符串明确写着"**步级失败不再即时 replan**"——细粒度纠偏曾经存在并被主动移除。步级纠偏的重建属于 `add-step-correction`。
- **重规划会整体替换计划**：`replan_node` 返回 `{"plan": 新计划, "cursor": 0, "skipped_task_ids": [], "early_finish": False}`。
- **重规划输入由 `_replan()` 组装**：`previous_plan` + `_compact_results_for_replan()` 的三元组 + `error[:500]`。压缩函数读 `item.get("id")`，而真实执行记录使用的键是 `subtask_id`。
- **失败工具去重已存在**（`replan_node`），但判据是 `status ∈ {empty_data, error, budget_denied, approval_denied}`。
- **状态里没有存放"运行期提取到的结构化事实"的键**。既有语义相近的键是 `intent.slots`（意图槽位）与 `extra_system_hints`（系统提示文本片段）。

## Goals / Non-Goals

**Goals**

- 让技能文档中的结构化事实（资产名称与位置）进入状态，并被重规划与后续子任务复用。
- 让重规划输入携带结果归属与已试路径，并保证该输入内部不自相矛盾。
- 把重规划收窄为**最后手段**：至多一次，且只在方向性错误时触发。
- 把三类不该进入规划器的注入块挡在外面。
- 修正"步骤提示"判定的依据，使其不再由子串巧合触发。
- **不新增任何模型调用**——否则是用 token 换 token。

**Non-Goals**

- 不改工具实现、工具白名单算法与工具参数；不新增工具。
- **不删除重规划节点**（理由见 D10）。
- **不改执行器的控制协议**：收缩（跳过 / 提前收尾）语义保持原样；"换源"这一档属于 `add-step-correction`，不在本变更内。
- 不重构提示词模板的整体结构，不引入模板引擎。
- 不为省 token 引入摘要模型、提示词缓存或响应缓存。
- 不调整 `agent/agent-goal`、`agent/plan-execute-control`、`agent/plan-subtask-allocation` 的既有行为。

## Decisions

### D1：结构化事实的提取点放在执行层读取技能文档之处

技能文档只在运行期由 `file_read_tool` 读取，改写阶段看不到它，因此提取点只能是执行层。

**备选（否决）**：在提示词里要求子任务模型"结论务必带上数据路径"。否决理由：这是把确定性事实交给概率模型，正是本次事故的成因。

### D2：提取方式用文档结构做确定性解析，而不是再调一次模型

技能文档的「数据资产地图」是规整的 Markdown 表格，可确定性解析出资产名与位置。

**备选（否决）**：用小模型做结构化抽取——多一次调用，且仍可能遗漏。

**回退**：解析不到任何事实时保持既有行为——不注入空集合、不中断链路（spec 已要求）。

### D3：结构化事实用新增的状态键存放，不塞进 `intent.slots`

`slots` 的语义是"意图槽位"，且会被 Pipeline 的 `_merge_slots()` 覆盖；运行期提取物放进去会造成语义混乱且可能被覆盖。

**备选（否决）**：放进 `extra_system_hints`——那是给系统提示用的文本片段，不是结构化数据。

### D4：重规划的结果归属修正"读取键"，而不是让上游再补一个 id

实测每条 `id` 为 `null`，因为压缩函数读 `item.get("id")`，而权威键是 `subtask_id`。

选择修正读取键并附带"无归属时显式标记"，而不是在结果里新增一个 `id` 字段：上游已有一份权威键名，两处各写一份必然漂移（与 `agent/agent-goal` 的单一真源取向一致）。

### D5：已试路径从工具调用记录确定性推导，不依赖模型结论

判据是该次工具调用的**入参**（路径 / 查询条件）加上**是否取得有效数据**。

**备选（否决）**：让子任务模型在结论里写"我试过哪些路径"——本 trace 中模型恰恰丢掉了这个信息，且同 D1 的理由。

### D6：矛盾拦截放在重规划输入发出之前，做一次确定性校验

判据：失败原因文本中出现的位置 / 查询，是否已存在于"已试且未取得有效数据"集合中。

处理：命中则从失败原因中**移除该条建议**并留痕，而不是丢弃整段失败原因（后半段往往仍有用）。

**备选（否决）**：在提示词里要求模型不要这样写。否决理由：本 trace 已证明自由生成的建议会与确定性事实直接矛盾，且无任何机制拦截。

### D7：步骤提示判定改为"词级"，且产物不再是整句问题

两个必要条件同时满足才算命中：

1. 匹配到的步骤标记**不落在某个词的内部**（例如"优先"里的"先"不算）；
2. 去除步骤标记后，剩余内容仍然表达步骤语义。

命中后只输出步骤语义片段；**不再返回整句问题**。

**备选（否决）**：只把正则列改成多字词（`首先|第一步|步骤`）。否决理由：仍是子串匹配，换一个词又会漏；且没有解决"返回值是整句问题"这个更根本的问题。

### D8：技能说明在规划侧只保留清单

规划器需要的是"有哪些技能可用"；"如何读取、如何遵守"属于执行期职责。

**备选（否决）**：两处都保留完整说明。否决理由：同一份执行指引被两个环节各承担一次，且实测规划器因此把"读取技能文件"排成了一个子任务。

### D9：意图锚点的置信度门槛做成配置项

置信度**缺失或非法一律按"不足"处理**，不得默认视为达标。

**备选（否决）**：硬编码阈值——不同业务的意图置信度分布不同。

### D10：重规划收窄为"方向性错误 + 硬上限一次"，但不删除节点

**正向条件（唯一）**：全部子任务结论均为**跑题**（有内容但无一涉及问题的核心实体、指标或时间）。缺口性质由 `summarize_node` **结构化给出**，不再依赖自由文本推断。

**硬上限**：同一轮至多一次（现有 `max_replan` 默认 2 → 改为 1）。

**显式排除**：缺口只是"未取得有效数据"（方向正确）；或所有候选工具已被证明未取得有效数据（重规划只会重复已失效路径）。

**为什么不删节点**：重规划与步级纠偏解决的是两类不同的问题——

| 场景 | 谁能救 |
|---|---|
| 计划方向对，某步没拿到想要的数据 | 步级就地纠偏（`add-step-correction`，0 额外调用） |
| **计划方向本身错了**（问题被理解错、整体思路错） | 只有重新规划能救 |

删掉节点，第二类情形会退化成"拿已有的错答案收尾"；而能力不会消失——它只会被塞进 execute 节点，复杂度不减，还丢掉状态机的可观测性。

**备选（否决）**：直接删除 `replan_node`。否决理由见上。
**备选（否决）**：保留现有触发条件只改次数上限。否决理由：触发条件才是成本大头——`insufficiency_signal` 由自由判定产生，它同时覆盖"方向错了"和"某步空了"，不区分就会让步级问题继续付整轮的代价。

## Risks / Trade-offs

| 风险 | 缓解 |
|---|---|
| 技能文档格式不规范，提取不到事实 | D2 的回退路径：不注入空集合、不中断；读取侧一律"缺失即视为空" |
| 词级判定收紧后，真实步骤表述被漏判 | 严格按「先…再…最后…」与「步骤/第 N 步」两类完整表述判定；漏判只会退回默认模式，不会中断链路 |
| 矛盾拦截误伤：建议中的位置与已试路径同名但语义不同 | 只做"位置字符串出现在已试且为空集合中"这一确定性判断；命中仅移除该条建议，整段失败原因保留 |
| 新增状态键在 checkpoint / resume 时缺失 | 按 `AgentGraphState` 既有约定给默认值，读取侧全部按"缺失即视为空"处理 |
| 置信度门槛调高后意图锚点长期不注入 | 门槛可配置；不注入的后果是退回"无意图约束"，与既有"缺失不得阻断链路"取向一致 |
| 收窄重规划后，部分原本会被救回的情形改为诚实收尾 | 有意的取舍；要求留下"判定被排除"的可观测记录，便于事后统计有多少请求受此影响 |
| 重规划从 2 次降到 1 次会降低救回率 | 与收窄同时生效。若观测到明显下降，应优先加强执行期纠偏（`add-step-correction`），而不是放宽触发条件 |

## Migration Plan

无数据迁移。改动集中在提示词组装、输入压缩与一个新增状态键。

- **部署**：随代码一起发布，无顺序依赖。
- **回滚**：`git revert` 本变更提交即可。新增状态键在回滚后留下的残留数据不会影响旧链路（旧代码不读该键）。
- **旧 checkpoint**：不含新键，读取侧按空处理，不影响恢复。
- **行为变化的观测**：重规划次数上限由 2 降为 1，属可观测的行为收紧；上线后应对比重规划发生率与救回率。

## Open Questions

- 重规划次数上限（现定 1）与"方向性错误"的唯一判据（全部结论跑题）都属于**保守初始值**。若上线后观测到"方向确实错了却未被识别"，应扩展判据而不是放宽次数——这一点不构成对本变更方案或任务拆分的影响，可安全地按观测数据调整。
