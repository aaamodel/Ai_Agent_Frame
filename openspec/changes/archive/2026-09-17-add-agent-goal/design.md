## Context

动机见 `proposal.md - Why`。此处只补充设计所必需的现状约束：

1. **改写阶段已是"单次调用产出多字段"的形态**：`AgentRewriteSchema` 当前一次产出改写、拆分、复杂度、建议工具、建议技能、显式步骤提示六类信息；「改写 + 意图」是组合调用，本就不止一次来回。
2. **schema 描述会逐字进入 response_format**：该文件明确记载整份 schema 约 3.8KB / 1.1k token，且**每次改写调用都要带上**。因此新增字段的 `description` 必须极简，否则是"每次调用都付费"的常驻成本。
3. **slots 已有"顶层键"先例**：`explicit_plan_hint` / `initial_plan_hint` / `first_tool_hint` 都是 `slots` 下的顶层键，由 `_merge_slots` 统一写入。
4. **ReAct 两种协议共用同一个系统附加段**：`build_extra_system(state)` 同时服务 Function Calling 与文本协议（分别在两处调用），是 ReAct 侧唯一的注入点。
5. **上一个变更刚确立了"不维护第二份状态"的原则**：台账状态由 `plan` + `subtask_results` 推导，state 只存"无法推导的模型决策"。
6. **改写侧有两条链路，且它们的形态不同**：
   - **主链路**：「改写 + 意图」组合单次调用，使用 `agent-rewrite-intent-combined.st` 与 `AgentRewriteIntentCombinedSchema`；
   - **降级链路**：组合调用失败或返回空时，`AgentCombinedRewriteIntentService.rewrite_for_agent` 显式 `super().rewrite_for_agent(...)` 回退到父类的两段链路，使用 `agent-question-rewrite.st` 与 `AgentRewriteSchema`。

   关键结构性事实：**组合 schema 是基类 schema 的子类**，且两条链路的解析统一走父类 `_parse_agent_rewrite`。这带来两个好处——字段只需在基类加一次、归一化只需写一处。但**提示词不是继承的**：两个 `.st` 文件必须分别修改。

## Goals / Non-Goals

**Goals**

- 每个决策点持有同一个目标锚点，且**不新增任何模型调用**。
- 注入带来的常驻输入成本可控（目标 ≤ 一句话；schema 增量**实测 178 字节**，高于原估的 ~120 字节，原因见风险表）。
- 目标缺失时链路不中断。
- 注入路径单一，不存在"三处各自读、各自兜底"的漂移风险。

**Non-Goals**

- 不让 `agent_goal` 承担任务拆分或复杂度判断（那是 `complexity_analysis` 的职责）。
- 不用它替代计划台账（台账描述"每个子任务如何"，目标描述"整体为何"）。
- 不改动意图识别本身的匹配逻辑。

## Decisions

### D1：由改写阶段产出，不新增调用

**决定**：`agent_goal` 作为 `AgentRewriteSchema` 的一个新字段。

**理由**：改写阶段是唯一同时看到「用户原问题 + 多轮历史 + 工具/技能清单」的 LLM 环节，目标抽象所需的全部输入都在那里；且该环节已是组合调用，新增字段不产生额外往返。

**备选（已否决）**：① 在意图聚合阶段单独产出——意图聚合主要是向量/规则打分，加 LLM 就是新增调用；② 用规则从原问题抽取——无法产出"交付物形态"的抽象。

### D2：承载在 `slots["agent_goal"]`，不新增状态字段

**决定**：改写结果 → Pipeline `_merge_slots` 写入 `slots["agent_goal"]` → 随 `intent.slots` 进入图状态。**不新增** `IntentContext` 字段，**不新增** `AgentGraphState` 字段。

**理由**：`slots` 已经是"Pipeline 决策层分析结果"的标准承载物（`explicit_plan_hint` 等先例），沿用它可以零改动地完成序列化与 checkpoint；新增平行字段会制造第二份真源——这正是上一个变更刚规避的问题。

**备选（已否决）**：新增 `AgentGraphState.agent_goal` 专用字段——与 `intent.slots` 内容重复，且需要在 `make_initial_state` / `intent_to_dict` 两处同步维护。

### D3：注入台账——是，但作为首行而非表格列

**决定**：`render_plan_ledger` 增加可选的目标参数，渲染为台账块**表格上方的独立首行**。

**理由**：
- 「跳过子任务 / 提前收尾」的判断恰好发生在读取台账的那一刻，目标必须紧邻这个决策，而不是散落在别处；
- 台账本就在每一步注入，因此新增一行（约 20~30 字）的边际成本近乎为零；
- **但不能作为表格的一列**：目标不是"某个子任务的属性"，它是所有子任务共同的约束；作为列会让 N 行重复同一段文字，纯浪费且稀释信息。

**备选（已否决）**：① 只放在系统提示段——位置与决策点距离过远；② 作为表格列——重复 N 遍。

### D4：三处注入同一份内容

ReAct 系统附加段、计划模式规划提示词、子任务执行提示词——三处都必须注入，且内容一致。

**理由**：三种决策分别在三处发生（ReAct 决定下一步调什么工具；规划决定拆几步；子任务执行决定跳过/收尾）。只注入其中一处，就等于另一种模式下仍然"不知道目标"。

### D5：归一化集中在解析层，读取走单一辅助函数

**决定**：在改写解析处完成 strip + 截断 + 空值兜底（回退改写后问题）；下游三处注入统一通过一个读取函数取得目标。

**理由**：如果让三个注入点各自兜底，会出现"一处回退到改写后问题、另一处注入空串"的不一致——这与上一个变更里"同一事实必须单一口径"的教训同源。

**额外收益（来自 Context 第 6 条）**：两条改写链路的解析都收敛在父类 `_parse_agent_rewrite`，因此归一化写在这一处，主链路与降级链路的行为自动一致，不需要写两份。

### D6：写法与长度约束

**定义**：`agent_goal` = 本次调用的**验收标准**——完成时必须交付的最终产物 / 结论形态。

**决定**：提示词侧对以下五条做零容忍校验。

1. **长度**：一句话，**≤ 60 字**；超出时模型须按「交付物 + 关键约束 + 结论」的优先级自行压缩。
   ⚠️ 压缩是**提示词侧**对模型的要求；解析层只做**硬截断**兜底（见 D5），**不在代码里实现"智能压缩"**。
2. **只写结果，不写过程**：只写交付什么 / 得出什么结论，不写怎么做。
3. **禁止复述**：禁止复述原始问题或改写后问题（`rewrite`）；禁止写成步骤分解。
4. **禁止词表**（命中即视为不合格）：
   - 步骤词：先、首先、然后、接着、最后、步骤、计划、第 1 步；
   - 空话：帮助用户、满足需求、解决问题、回答用户。
5. **与 `explicit_plan_hint` 的分工**：plan hint 允许列步骤，`agent_goal` 不允许——同一调用内产出，两者语义不得重叠。

**唯一例外**：当本轮产物本身就是一份步骤清单时，只写「交付操作步骤清单」，而不是把步骤逐一列出来。

**输出位置**：改写输出 JSON 中，在 `rewrite` 之后新增一行：
`"agent_goal": "一句话≤60字，最终交付物/结论形态；非问题复述，非步骤计划"`

**理由**：不约束的话，模型很可能把它写成第二个 `rewrite`（复述问题）或第二个 `explicit_plan_hint`（步骤列表），既浪费每次调用的上下文，又让字段语义重叠。给"步骤清单类产物"留例外，则是避免约束走向另一个极端——把合法目标也误判成违规。

### D7：`description` 极简

字段描述控制在**一行、不含示例**。

**理由**：见 Context 第 2 条——描述会逐字进入每一次改写调用的 response_format，属于常驻成本；示例性内容放提示词文件（那里是单次注入的 system 内容，且已承载同类约束）。

### D8：`agent_goal` —— 契约层必填，校验层容错

**决定**：两层分开处理，缺一不可。

| 层 | 做法 |
|---|---|
| **契约层**（给模型的 json_schema） | `agent_goal` **100% 留在 `required` 中**——模型被明确要求输出该字段 |
| **校验层**（我们的代码） | **对该字段单独容错**：模型没输出好（缺失 / 空串 / 类型不对 / 火星文）时，把该字段置空后**重新校验并保留其余字段**（`validate_tolerating_agent_goal`） |

**理由**：两层解决的是不同问题。契约必须硬——否则模型会常态化偷懒不输出；但
"模型偶尔没输出好"属**极端事件**，我们接受：只表现为"本轮目标没起作用"＋按 D5 回退，
**整条 agent 编排照常跑完**。若把契约的严格性直接落到校验层（`required` 不做容错），
一个字段的缺失会把**整次改写**连带报废——strict 未严格执行时（本仓已知 qwen 系
存在这种情况）`model_validate_json` 整体失败 → 落到 `parsed_result or fallback_result`
的规则兜底 → **其余本来正确的字段一并丢弃**。字段级缺失不该升级成链路级失败。

**容错边界（刻意收窄）**：只在**报错全部落在 `agent_goal` 上**时容错。
`rewrite` / `complexity_analysis` 等字段仍走原有严格校验——不做无差别放宽，
否则真·畸形输出（例如同时漏掉 `rewrite`）会被静默接受。

**两个解析点都要容错**（漏一个就会退化）：

- 降级链路 `_parse_agent_rewrite`：改写字段本身；
- 主链路 `_extract_precomputed_scores`：意图打分——若只改前者，Stage2 会因
  "没有预计算打分"而退回旧的两段链路，白白多一次 LLM 调用。

**可观测性**：解析层 `logger.warning` 标记"模型未提炼出验收标准"；
trace 上 `agent.goal.source=fallback` 代表本轮没拿到模型产出的目标。

**备选（已否决）**：① 字段设为可选（带默认值）——契约变软，模型会常态化不输出；
② `required` 且不做校验层容错——字段级缺失升级为链路级失败（即最初写法）。

## Risks / Trade-offs

| 风险 | 缓解措施 |
|---|---|
| 模型把它写成"改写后问题的副本"，字段失去价值 | D6 的写法约束 + 提示词零容忍校验；通过 trace 抽查目标质量 |
| 每次改写调用的 response_format 变大 | D7 极简描述。**实测增量 178 字节**（原估 ~120 偏低：除 key + description 外，pydantic 还会自动生成 `"title": "Agent Goal"`）；每次改写调用固定多付这一点，可接受 |
| 三处注入导致输入体积上升 | 目标 ≤ 60 字；ReAct 侧每轮 +1 行，计划侧每步 +1 行 |
| 目标是本轮还是本会话的目标发生歧义（多轮对话） | 约束为"结合历史消解指代后，描述**本轮**要达成的目标" |
| 模型漏输出该字段 | **契约层必填 + 校验层容错**（见 D8）：schema 里仍是 `required`（模型被明确要求输出），但校验层对该字段单独容错——缺失 / 空串 / 类型不对 / 火星文都只置空该字段并**保留其余字段**，按 D5 回退为改写后的问题，**整条编排照常跑完**（该轮目标"没起作用"可以接受）。解析层日志标记，trace 上 `agent.goal.source=fallback` 可观测发生率。**实测**：3 个真实请求（含「你好」退化输入）模型均照常输出该字段 |
| 目标与实际执行脱节（模型说了但没做到） | 不在本变更解决：收尾阶段已有证据充分性判定会拦住"没做到却宣称完成" |

## Migration Plan

1. 无数据迁移、无外部依赖变更。
2. schema 新增字段属**向后兼容**：模型未输出时走 D5 兜底，因此可先上线再观察质量。
3. 回滚方式：停止注入即可（字段与兜底可保留，不影响其他链路）。
4. 上线后需在 trace 上确认两件事：① 目标是否稳定为"交付物形态"而非问题复述；② 跳过/提前收尾的触发是否因目标注入而变得更合理。
