## Context

动机见 `proposal.md - Why`。此处只列影响**方案选择**的现状与约束（均为本次实地核实）：

1. **`raw_data/sales_intel` 实际有 6 个 xlsx、18 个 sheet**，按本次确认的三类切分：

   | 分类 | sheet | 现状行数 |
   |---|---|---|
   | 业务 → SQLite | 线索总表 45 / 输赢单明细 34 / 市场活动明细 12 / 动态时间线 12 / 月度汇总 12 / 竞品档案 6 / 产品目录 7 | **128 行** |
   | 规则 → RAG | 字段字典 ×5 / 阶段流转规则 / 折扣权限 / 组合策略 | 8 张 |
   | 派生 → 不存 | 季度汇总 / 区域产品透视 / 原因分类 | 3 张 |

   扩量后业务表为 **512 行**（净增 3 倍）。

2. **`vanna` 与 `chromadb` 当前均未安装**，属新增依赖（`chromadb` 体量较大）。

3. **参照实现 `vanna_sql.py` 的关键形态**：`MyVanna(ChromaDB_VectorStore, OpenAI_Chat)`、
   硬编码 DashScope OpenAI 兼容端点 + `qwen3.7-plus-2026-05-26`、ChromaDB 本地目录、
   `generate_sql_tool` 与 `execute_sql_tool` 两个 langchain `@tool`、以及从
   `sqlite_master` / `information_schema` 增量同步 DDL 的训练逻辑。

4. **`local_excel_*` 被约 30 个文件引用**（意图树 8 处、`SKILL.md` 16 处、`planner`/
   `summarize_node` 提示词、`config.py` 危险名单、`init_tools.py`、evals 5 处、测试 4 个）。

5. 项目**无迁移框架**，`app/main.py` 启动期执行幂等轻量 DDL（既有惯例）。

## Goals / Non-Goals

**Goals:**

- 业务数据以带显式约束的 SQLite 表为权威存储；模型看到的 schema 是确定的，不再猜。
- 执行期用一句自然语言取数，替代"文件路径 + 工作表名 + 过滤列 + 聚合列"的参数拼装。
- 写入保留"0 命中拒绝 / 多命中拒绝"护栏，并升级为参数化 SQL（防注入）。
- 删除 Excel 取数工具，并**同步清理全部约 30 处引用**，不留悬空。
- 业务表行数扩至 4 倍，且扩量数据满足全部约束与业务口径。

**Non-Goals:**

- **不引入 PostgreSQL 与多引擎路由**——参照实现里的 pg 分支、跨库 `JOIN`、
  `schema_to_engine` 路由表**全部不搬**。
- **不删除 xlsx 文件**——保留为导出视图。
- **不改 RAG 检索算法**——规则类 sheet 走既有 `rag_knowledge_search` 通道。
- **不提供业务员改数据的前端**（见 Risks）。
- **不删除既有 `agent/excel-query` 主 spec**（需 MODIFIED/REMOVED delta，留作后续）。
- **不把 SQL 工具的模型调用接入 ModelRouter**（本次明确例外，代价见 Risks）。

## Decisions

### D1：SQLite 库放在仓库内，连接按需建立并复用

库文件置于 `data/sales.db`（或 `raw_data/sales_intel/sales.db`），与数据同域、可提交。
工具持有一个长连接（`check_same_thread=False`），避免每次调用重开文件。

- 选它的理由：45→180 行这个量级，SQLite 是单文件、零运维的最优解；放仓库内可被版本管理。
- 备选：启动时把库 `ATTACH` 到 `:memory:`（参照实现的做法）。**否**——内存库进程重启即空，
  且需要每次启动同步 DDL，对本项目没有跨库查询的需求。

### D2：先 `CREATE TABLE`（带约束）再 `append` 灌数据，不用 `to_sql(replace)`

`df.to_sql(..., if_exists="replace")` 会按 dtype 推断建表，**不会**生成 `PRIMARY KEY`
与 `CHECK` 枚举约束——那正是本次要解决的核心（约束不可见 = 模型继续猜）。

因此：先按字段字典手写 `CREATE TABLE`（主键 / 类型 / `NOT NULL` / 枚举 `CHECK`），
再用 `to_sql(..., if_exists="append", index=False)` 灌数据。

- 附加约束：导入前 MUST 先校验数据能通过约束，避免"部分成功"造成半张表。

### D3：两个工具，而不是照搬参照实现的"生成 + 执行"双工具

参照实现把流程拆成 `generate_sql_tool` + `execute_sql_tool`，让模型先拿 SQL 再执行。
本项目**不照搬**，改为：

1. `sales_sql_query(question)` —— 一句自然语言直接返回结果，返回值里**附上生成的 SQL**
   供审计与自我校验；
2. `sales_sql_write(...)` —— 语义更新，内部参数化为 `UPDATE`。

- 选它的理由：本项目每次工具调用都要模型决策一轮，拆两步会让"取一次数"变成两轮决策，
  并把 SQL 塞进对话历史（挤占上下文）。合一后 SQL 仍随结果返回，可审计性不降。
- 备选：照搬双工具。**否**——与"减少参数、减少往返"的初衷相悖。

### D4：写入用语义参数 + 参数化 SQL，绝不接受裸 SQL

`local_excel_write_tool` 的 `filter_column + filter_value + target_column + new_value`
映射到：

```
UPDATE <table> SET <target_column> = ? WHERE <filter_column> = ?
```

- **列名不能参数化**，因此列名 MUST 用 `PRAGMA table_info` 的真实列清单做白名单校验，
  不匹配直接拒绝（这一条同时替代了旧工具里的 `difflib` 模糊匹配——有了 schema，
  不再需要猜）。
- **值必须参数化**（`?` 占位符），MUST NOT 字符串拼接，防止注入。
- 命中数护栏：`rowcount == 0` → 拒绝；`rowcount > 1` → 拒绝并列出行。
- 写入 MUST 登记进 `config.py` 的危险工具名单，走既有审批。

### D5：DDL 训练数据从 `sqlite_master` 增量同步

照搬参照实现的增量同步思路（新增 → 训练；变更 → 删旧训练新；删除 → 移除训练数据），
但**只保留 SQLite 分支**：读 `sqlite_master` 的 `sql` 字段。

- 同步时机：工具初始化时执行一次；并提供手动触发入口（建表/改表后）。
- 选它的理由：schema 知识 MUST 与实际库同源；硬编码表名清单会随表结构变化而失效。

### D6：LLM 与向量模型硬编码，明确不走 ModelRouter

按参照实现硬编码：DashScope OpenAI 兼容端点 + `qwen3.7-plus-2026-05-26` +
本地 ChromaDB 目录 + 集合名。Key 从环境变量 `DASHSCOPE_API_KEY` 读取。

**这是有意为之的例外，代价必须被显式接受**：

- 不受多厂商方言适配、熔断降级保护——该通道挂了就是挂了；
- 不进调用预算账本（`platform/llm-call-budget`）——预算口径会少算一部分；
- 不进 Langfuse 追踪——排障时这一路的调用是盲区。

缓解：工具 MUST 在初始化失败时**明确报错**（而不是静默不可用）；并在返回中标注
"本次结果由外部模型通道生成"。预算与追踪的接入留作后续。

### D7：规则与口径**分流**，不做"8 张 sheet 全量进 RAG"

实地读内容后发现这 8 张 sheet **不是一类东西**，混在一起会导致把冗余注入 RAG：

| 实际内容 | 真实例子 | DDL 里有没有 | 去向 |
|---|---|---|---|
| 列名 / 类型 / 枚举取值 | `行业 = 制造业/零售连锁/…` | **有**（`CHECK` 里） | **不进 RAG**——Vanna 已从 DDL 学到，重复注入是浪费 |
| 业务口径 / 判据 | `员工规模：用于ICP判定（≥200为达标）` | 没有 | **训练进 Vanna documentation**（D7b） |
| 纯规则 | `销售代表：折扣下限9.5折`；`低于8.5折需总经理` | 没有 | RAG（并入 `sales_kb`） |
| 流程规则 | `MQL 进入标准=符合ICP且有行为信号` | 没有 | RAG |

- 纯规则并入既有 `sales_kb` 集合（不新建）：当前集合只有 8 个，新开集合会增加路由选项、
  摊薄检索；规则与销售业务同域，语义连贯。
- 备选：新建 `sales_rules` 集合。**否**——本次不增加路由面。
- 备选：字段字典整张进 RAG。**否**——其中列名/类型/枚举部分与 DDL 重复，
  真正有价值的是"说明"列里的口径，应单独提取（见 D7b）。

### D7b：口径必须**预置**进 SQL 生成，不得依赖模型先检索

以"ICP 达标的线索有多少"为例，模型必须知道 `ICP 达标 = 员工规模 ≥ 200` 才能写出
`WHERE 员工规模 >= 200`。这个知识只在字段字典的"说明"列里，DDL 里没有。三条路：

- **A 两段式**（模型先 `rag_knowledge_search("ICP判定标准")` 再 `sales_sql_query`）：
  **否**。多一轮调用、RAG 未必命中，且**要害是"指望模型自觉去查"**——这与 Excel 时代
  指望模型自己猜对列名是同一个错误。
- **B 预置进 Vanna**（`vn.train(documentation=...)`）：**采用**。零额外调用、不依赖模型
  自觉，口径与 schema 在同一处注入。已核实 vanna 0.7.3 的 `train()` 签名含
  `documentation` 参数。
- **C 术语映射表 / 血缘图谱**：**否**（当前规模过度设计）。7 张表 / 473 行需要的不是治理
  系统，是几十条口径注释。

⚠️ 需要澄清一个类比：**"血缘治理"回答的是"字段从哪来、改上游影响谁"（变更影响分析）**，
而字段字典/口径回答的是**"业务词对应哪些列、什么算达标"（语义映射）**。同属元数据治理，
但不是一回事。

**入口形态**：口径的写入做成**脚本**（`python -m app.core.sales_db.train_vanna`），
不做 HTTP 路由。理由：口径是需要评审的业务资产，走版本控制 + 脚本可复现、可追溯；
做成运行时上传接口会让口径失控（可被随意修改且无痕迹）。
DDL 训练**不需要**任何人工介入——沿用参照实现的模块级增量同步（见 D5）。

### D7c：工具编排不做固定前置，顺序由问题结构决定

存在真正需要两个工具协作的问题，但**顺序不是"RAG 永远在 SQL 之前"**。例如
"这单按折扣权限能不能批？"：先 `sales_sql_query` 取金额与销售代表，再
`rag_knowledge_search` 取该等级的折扣下限——**先有数才能比对规则**。这类问题让模型多调
一次工具是合理的，不需要特殊机制，也**不得**在提示词里写死"先检索再查询"。

### D8：扩量用脚本生成，且必须受约束校验

- 生成策略 MUST 只使用既有枚举取值与既有负责人/区域/产品线等维度组合，
  MUST NOT 发明新的枚举值；
- 关联字段（如输赢单的 `线索编号`）MUST 从扩量后的线索表取值，保证无孤儿；
- 生成后 MUST 跑一次全表约束校验（导入即校验，见 D2）。

### D9：实施顺序——先立新，再改契约，最后删旧

```
① 建库建表 + 导入 + 扩量      → 数据先行，可独立验证
② 实现 SQL 工具并注册         → 新旧并存，此时两套都能用
③ 切换契约（意图树/技能/提示词/危险名单/evals/测试）→ 路由全部指向新工具
④ 删除 localexcel.py / excel_query.py 与注册      → 最后摘除
```

- 选它的理由：若先删旧工具再改契约，中间态会出现"路由指向已删除工具"的不可用窗口。
  新旧并存期间两套工具都在，任何一步都可回退。

## Risks / Trade-offs

- **`vanna` / `chromadb` 未安装且体量大** → 先单独验证安装与首次 DDL 训练耗时；
  若 chromadb 在本机不可用，退路是改用 Vanna 的其他向量存储实现（需重新确认）。
- **SQL 工具不走 ModelRouter，是盲区** → 初始化失败明确报错；结果中标注通道来源；
  预算与追踪接入列为后续项（D6）。
- **`agent/excel-query` 主 spec 依然存在但工具已删除** → 本变更**不**删除该 spec
  （需 MODIFIED/REMOVED delta）。这是已知遗留，必须在归档前处理，否则主 specs 里会
  留下一份描述已不存在工具的需求。
- **业务员仍在 Excel 里改台账 → 库与文件不同步**（进库的经典代价）→ 本次不解决；
  库为权威，xlsx 为导出视图。若后续需要从 xlsx 回灌，需另开变更做同步链路。
- **规则类文本化后进 RAG，可能稀释检索** → 8 张规则表文本量不大；回归时确认
  `sales_kb` 的检索命中率不下降（需要变更前的基线，若无基线则记录为已知缺口）。
- **工具集变化会让 evals 基线整体位移** → 评测集与 schema MUST 同步更新；
  `evals/test_eval_gate.py` 的断言若绑定旧工具名会直接失败，属预期内需同步改造。

## Migration Plan

1. 安装 `vanna` / `chromadb`，确认 DashScope Key 可用。
2. 建库建表（带约束）→ 从 xlsx 导入 → 校验约束 → 扩量至 4 倍 → 再校验。
3. 实现并注册 SQL 工具（新旧并存），手动跑通一条自然语言取数与一次受约束写入。
4. 切换契约：意图树 / `SKILL.md` / 提示词 / 危险名单 / evals / 测试。
5. 删除 `localexcel.py` / `excel_query.py` 与注册，重跑全量回归 + 全仓引用扫描。
6. **回滚**：步骤 ④ 之前均可逐段回退（新旧并存）。步骤 ⑤ 之后回滚需恢复两个文件与
   注册；数据侧删除库文件即可（xlsx 始终保留，故业务数据不会丢失）。
